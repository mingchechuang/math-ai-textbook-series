# 第 30 章　整合專題：可稽核養殖數位分身

## 學習目標與先備知識

本章把本卷的幾何、渲染、動畫、影像與場景資料串成一個可重現的合成養殖場專題。完成後，你應能：

- 組織一個包含場景、動畫、相機、渲染輸出及標註的專案目錄。
- 用明確的座標、單位、時間與資料欄位描述每一影格。
- 建立可由標準庫 Python 執行的小型合成資料流程。
- 追溯影像與標註的來源參數，區分模擬資料、實測資料及控制指令。
- 設計唯讀查詢介面，讓程式或 agent 查詢合成場景並回報依據。

先備為本卷的向量、矩陣、相機、網格、光柵化、變換、關鍵影格及合成資料概念，以及 Python 基本語法。核心實驗不要求GPU、Blender、網路或第三方套件；以下程式輸出簡化的PPM影像、JSON資料及場景清單。它不模擬真實水下光學、魚類生態或養殖設備。

## 問題與直覺

數位分身專題常有多種資料：場景幾何、相機參數、動畫狀態、渲染影像、物件遮罩或ID、深度，以及供人或程式查詢的摘要。若它們各自生成，卻沒有共同的影格編號、時間戳與參數來源，影像便難以追溯：畫面中的魚是哪個物件？相機當時在哪裡？動畫時間是多少？標註是否對應同一影格？

本章把「可稽核」定義為：每個輸出都能透過清單與固定識別碼，追溯到產生它的場景、設定、時間與生成流程；每個欄位也明確標出單位、座標系及其為模擬或實測。可稽核不等於正確描述真實養殖場，也不等於已驗證物理準確度。

專題流程如下：

1. **場景定義**：列出池體、合成魚體、相機及其座標系。
2. **動畫取樣**：用固定時間步算出每條魚的位置與朝向。
3. **渲染**：生成影像，並同時生成物件ID等可對照的標註。
4. **清單記錄**：保存每影格時間、相機、物件狀態、輸出檔名及生成參數。
5. **唯讀查詢**：從清單和標註回答「某影格有幾條魚？」等問題，並提供所依據的影格與欄位。

本章的小型程式只將移動物件畫成影像中的圓形標記，以展示資料對應與追溯流程；它不是完整三維渲染器，也不輸出真實深度或水下影像。

## 數學與幾何推導

### 固定時間步與影格時間

令影格編號為整數 \(k\)，影格頻率為 \(f\) 影格／秒，則影格時間定義為

$$
t_k=\frac{k}{f}.
$$

這個時間是模擬時間，不必等於實際設備時鐘。以固定時間步更新狀態可使同一設定可重現；若採用可變時間步，則須把每一步的時間差一併記錄，否則僅有影格編號不能完整描述動畫取樣。

本章示範簡單的平移：

$$
x_i(t)=x_{i,0}+v_i t,
$$

其中 \(x_{i,0}\) 是第 \(i\) 條合成魚的初始位置（公尺），\(v_i\) 是速度（公尺／秒）。若模型只在二維影像平面移動，便不能由此推論它在三維池體中的真實位置或運動。

### 場景座標、相機與像素映射

世界座標採右手系：\(+X\) 向右、\(+Y\) 向上、\(+Z\) 由畫面向觀者。位置採直向量與齊次座標

$$
\mathbf{p}_h=(x,y,z,1)^T.
$$

相機觀察時，點依序經模型、視圖及投影變換：

$$
\mathbf{p}_{clip}=PVM\mathbf{p}_h.
$$

若採OpenGL式NDC，透視除法後的 \(x,y\) 位於標準化裝置座標範圍 \([-1,1]\)。但本章簡化程式不計算三維投影；它直接定義合成影像中的像素座標，以便專注於跨資料對應。

影像寬 \(W\)、高 \(H\)，像素索引 \(u,v\) 從左上角開始，像素中心為 \((u+0.5,v+0.5)\)。影像列索引向下增加，不能與世界座標的 \(+Y\) 向上混用。若要把範圍 \([x_{\min},x_{\max}]\) 映射到像素中心，簡化的水平方向映射可寫為

$$
u=\operatorname{round}\left(
\frac{x-x_{\min}}{x_{\max}-x_{\min}}(W-1)
\right).
$$

這是畫面座標映射，不是透視投影。使用時須確保 \(x_{\max}>x_{\min}\)，並限制結果在合法像素索引範圍內。

### 輸出、標註與追溯關係

令影格輸出為 \(I_k\)，影格標註為 \(A_k\)，場景與生成設定為 \(C\)。一個可追溯的生成關係可表示為

$$
(I_k,A_k)=G(C,k,t_k),
$$

其中 \(G\) 是固定的生成流程。清單至少要把 \(k,t_k\)、設定識別碼、影像路徑及標註路徑連在一起。若生成器版本或設定改變，就應變更其識別資訊，避免不同資料被誤認為同一批。

標註中的位置若採世界座標，欄位應明示單位與座標系；若採像素座標，則應明示像素原點、範圍和整數取整規則。物件ID應在整段序列維持穩定，不能以畫面中的左右位置臨時代替身份。

## 逐步手算例題

### 例一：固定時間與位置

某合成魚的初始水平位置是 \(x_0=0.20\) 公尺，速度 \(v=0.10\) 公尺／秒，影格率 \(f=5\) 影格／秒。求第3影格的時間與位置。

1. 影格時間為

   $$
   t_3=\frac{3}{5}=0.6\ \text{秒}.
   $$

2. 位置為

   $$
   x(0.6)=0.20+0.10\times0.6=0.26\ \text{公尺}.
   $$

此位置是所定義的簡化合成運動結果，不是量測到的魚體位置。

### 例二：映射到像素

影像寬 \(W=16\)，水平範圍設為 \([-1,1]\) 公尺。將 \(x=0.26\) 公尺映射到像素：

1. 正規化位置為 \((0.26+1)/(1-(-1))=0.63\)。
2. 像素索引為

   $$
   u=\operatorname{round}(0.63\times15)
   =\operatorname{round}(9.45)=9.
   $$

索引9表示第10個像素欄，因為索引從0開始。實際影像標記畫在此欄附近；影像像素不是世界位置的精確測量值。

## 實作與程式

以下完整程式只使用 Python 3.10+ 標準庫。它建立兩條移動標記、輸出小型PPM序列、輸出逐影格JSON標註，以及總體manifest。標記以不同整數ID表示；影像輸出的是簡單顏色，不是實際相機成像。

將程式存為 `digital_twin.py`。執行後會建立 `output/` 目錄：

```text
python digital_twin.py
```

```python
import json
import math
from pathlib import Path


WIDTH = 64
HEIGHT = 48
FPS = 4
FRAME_COUNT = 5
X_RANGE = (-1.0, 1.0)
Y_RANGE = (-0.75, 0.75)
OUTPUT = Path("output")

# 合成物件狀態：位置以公尺表示，速度以公尺／秒表示。
OBJECTS = [
    {"id": 1, "x0": -0.60, "y": -0.10, "vx": 0.20},
    {"id": 2, "x0": 0.35, "y": 0.25, "vx": -0.10},
]


def map_to_pixel(x, y):
    xmin, xmax = X_RANGE
    ymin, ymax = Y_RANGE
    if not xmin < xmax or not ymin < ymax:
        raise ValueError("座標範圍必須遞增")

    u = round((x - xmin) / (xmax - xmin) * (WIDTH - 1))
    v = round((ymax - y) / (ymax - ymin) * (HEIGHT - 1))
    return (
        max(0, min(WIDTH - 1, u)),
        max(0, min(HEIGHT - 1, v)),
    )


def set_pixel(image, x, y, color):
    if 0 <= x < WIDTH and 0 <= y < HEIGHT:
        image[y][x] = color


def draw_disc(image, cx, cy, radius, color):
    for y in range(cy - radius, cy + radius + 1):
        for x in range(cx - radius, cx + radius + 1):
            if (x - cx) ** 2 + (y - cy) ** 2 <= radius ** 2:
                set_pixel(image, x, y, color)


def write_ppm(path, image):
    with open(path, "w", encoding="ascii") as f:
        f.write(f"P3\n{WIDTH} {HEIGHT}\n255\n")
        for row in image:
            f.write(" ".join(
                f"{r} {g} {b}" for r, g, b in row
            ))
            f.write("\n")


def render_frame(frame_index):
    time_s = frame_index / FPS
    image = [
        [(18, 36, 54) for _ in range(WIDTH)]
        for _ in range(HEIGHT)
    ]
    annotations = []

    colors = {
        1: (240, 150, 50),
        2: (70, 210, 170),
    }

    for obj in OBJECTS:
        x = obj["x0"] + obj["vx"] * time_s
        y = obj["y"]
        u, v = map_to_pixel(x, y)
        draw_disc(image, u, v, 3, colors[obj["id"]])
        annotations.append({
            "object_id": obj["id"],
            "position_world_m": [x, y, 0.0],
            "position_pixel": [u, v],
            "source": "simulated",
        })

    return time_s, image, annotations


def test_mapping_and_ids():
    assert map_to_pixel(X_RANGE[0], Y_RANGE[1]) == (0, 0)
    assert map_to_pixel(X_RANGE[1], Y_RANGE[0]) == (
        WIDTH - 1, HEIGHT - 1
    )

    time_s, image, annotations = render_frame(0)
    assert time_s == 0.0
    assert len(annotations) == 2
    assert {item["object_id"] for item in annotations} == {1, 2}
    assert all(item["source"] == "simulated" for item in annotations)
    assert all(
        0 <= channel <= 255
        for row in image
        for pixel in row
        for channel in pixel
    )


def main():
    test_mapping_and_ids()
    OUTPUT.mkdir(parents=True, exist_ok=True)

    manifest = {
        "dataset_id": "synthetic-tank-demo-v1",
        "data_status": "simulated",
        "units": {
            "position_world": "m",
            "time": "s",
            "velocity": "m/s",
        },
        "coordinate_convention": {
            "world": "right-handed; +X right, +Y up, +Z toward viewer",
            "image": "origin upper-left; pixel indices increase downward",
        },
        "image": {
            "format": "PPM P3",
            "width": WIDTH,
            "height": HEIGHT,
            "channel_range": [0, 255],
        },
        "fps": FPS,
        "frame_count": FRAME_COUNT,
        "generator": "digital_twin.py",
        "frames": [],
    }

    for k in range(FRAME_COUNT):
        time_s, image, annotations = render_frame(k)
        image_name = f"frame_{k:04d}.ppm"
        annotation_name = f"frame_{k:04d}.json"

        write_ppm(OUTPUT / image_name, image)
        with open(OUTPUT / annotation_name, "w", encoding="utf-8") as f:
            json.dump(
                {
                    "frame_index": k,
                    "time_s": time_s,
                    "objects": annotations,
                },
                f,
                ensure_ascii=False,
                indent=2,
            )

        manifest["frames"].append({
            "frame_index": k,
            "time_s": time_s,
            "image": image_name,
            "annotation": annotation_name,
        })

    with open(OUTPUT / "manifest.json", "w", encoding="utf-8") as f:
        json.dump(manifest, f, ensure_ascii=False, indent=2)


if __name__ == "__main__":
    main()
```

輸出目錄預期如下：

```text
output/
  manifest.json
  frame_0000.ppm
  frame_0000.json
  frame_0001.ppm
  frame_0001.json
  frame_0002.ppm
  frame_0002.json
  frame_0003.ppm
  frame_0003.json
  frame_0004.ppm
  frame_0004.json
```

`position_world_m` 是合成世界位置；`position_pixel` 是本例映射後的影像索引。兩者不是同一座標系，不能用像素位置代替世界位置。程式把影格時間存為秒，影格率存入manifest，並把每個影格的標註路徑與影像路徑列入清單。程式不生成相機內外參、深度或真實場景量測；若後續加入這些欄位，必須一併定義單位、座標系與生成方式。

## 測試與預期結果

程式在生成輸出前呼叫 `test_mapping_and_ids()`。按程式定義，測試會檢查：

- 世界範圍的左上、右下映射至影像角落索引。
- 第0影格時間為0秒。
- 標註包含ID 1與ID 2，且來源標記為 `simulated`。
- 影像每個色彩通道均落在0至255。

程式執行後預期建立五組影格影像與JSON標註，並建立一份manifest。這是依程式邏輯描述的預期，未宣稱已執行或檢視檔案。PPM為文字格式，可用文字編輯器檢查；也可用支援PPM的本機影像檢視器查看，但核心流程不依賴特定檢視器。

手動驗收可逐項確認：

1. manifest中的影格編號由0連續至4，時間由 \(k/4\) 秒決定。
2. 每個影格都有對應PPM和JSON檔名。
3. 同一物件ID在各影格中保持一致。
4. PPM標頭尺寸為64×48，最大色彩值為255。
5. 每筆座標欄位的單位、座標系及 `source` 標記清楚。

## 除錯與常見陷阱

- **影格時間與影格編號錯位**：若影像從第0影格開始，時間通常也是 \(0/f\)，不是 \(1/f\)。要明確決定影格索引慣例。
- **影像Y軸與世界Y軸混淆**：程式把世界Y向上映射為影像列索引向下，因此映射公式有 \(y_{\max}-y\)。少了這個翻轉，影像位置會上下顛倒。
- **像素取整及邊界越界**：映射結果可能超出影像範圍，程式以限制操作夾在合法索引內。若不希望物件被夾在邊界，應另記錄物件出界狀態，而不是把夾取後位置當作原始位置。
- **把顏色或圓點誤認為真實觀測**：本程式畫出的標記是合成示意，不是攝影機影像、魚體分割結果或感測器讀值。
- **標註與影像使用不同狀態**：若影像與JSON分別以不同時間或不同物件位置生成，便會不一致。應讓兩者共享同一個 `render_frame` 狀態計算結果。
- **僅靠檔名追溯資料**：檔名可以改變或重複；manifest還應記錄資料集識別碼、影格編號、時間及相對路徑。
- **把模擬資料與實測資料混在一起**：資料來源欄位必須明確。如果混合資料，需對每個欄位或樣本分別標記來源，不能只在文件標題中說明。

## 養殖數位分身案例

本章示範的是一段合成池體影像序列。若要擴充成較完整的圖學專題，可按以下資料流分工：

1. **場景資料**：保存池體尺寸、魚體資產路徑、世界變換與材質識別碼；長度使用公尺。
2. **動畫資料**：保存固定影格率、每影格時間及每個穩定物件ID的變換。動畫軌跡是合成設定，不表示真實魚類行為。
3. **相機資料**：保存影像寬高、投影類型、內參、外參、近平面與遠平面；明示相機看向局部 \(-Z\) 的座標約定。
4. **渲染輸出**：每個影格輸出影像；若輸出ID遮罩或深度，另存為資料通道，不套用sRGB色彩轉換。
5. **標註與清單**：對每影格記錄物件ID、時間、相機識別碼、輸出檔案及來源狀態。若標註是從渲染場景直接取得，標成合成標註；若是人工或感測資料，另行說明其來源與處理流程。
6. **唯讀查詢**：查詢程式只讀manifest、影格JSON及合成標註，回答如「影格2有哪些物件ID？」並回傳資料集ID、影格編號與欄位名稱作為依據。

例如，查詢「第2影格有幾個物件？」可依據 `frame_0002.json` 中 `objects` 陣列的項目數回答。這個答案只描述合成資料；不能據此宣稱現場有相同數量的魚。

### 可稽核目錄與執行順序

建議把專案整理成以下結構：

```text
project/
  README.md
  digital_twin.py
  config.json
  output/
    manifest.json
    frame_0000.ppm
    frame_0000.json
    ...
```

- `README.md` 說明程式入口、執行命令、合成資料限制及欄位約定。
- `config.json` 保存場景與動畫設定；若程式使用內建設定，仍應在manifest註明。
- `digital_twin.py` 由設定生成影格與標註。
- `output/manifest.json` 指向每個影格的產物與時間。

建議執行順序為：先檢查設定與單位，再執行生成器，接著驗證manifest及影格數量，最後抽查一份PPM與JSON是否對應。不要以生成檔案成功作為影像品質、物理準確度或生態合理性的驗證。

### 唯讀 agent 查詢邊界

可在此資料上加一個只讀查詢程式，允許列出資料集識別碼、影格時間、物件ID及合成位置；回答時引用影格編號和欄位來源。它不應改寫場景、生成未記錄的感測值、連接真實設備或執行任何養殖操作。若問題超出資料範圍，應回答「清單未提供」，而非由合成動畫推測現實狀態。

## 習題

### 習題一：手算時間與像素

影格率為10影格／秒，第7影格中合成物件的位置為 \(x=0.25\) 公尺。水平範圍為 \([-1,1]\) 公尺，影像寬 \(W=21\)。計算影格時間與像素欄索引。

### 習題二：程式測試設計

若把程式的 `FRAME_COUNT` 改為8、`FPS` 改為2，列出至少三項應新增或修改的測試，確保影格時間與manifest一致。

### 習題三：反例與除錯

某系統只在檔名寫 `frame_0003.ppm`，沒有時間、資料集ID或標註路徑。使用者看到影格中的兩個標記，想詢問各自的世界位置。說明為何不能只從影像回答，並列出修復追溯能力所需的欄位。

### 習題四：整合應用

設計一個唯讀查詢，回答「資料集的第 \(k\) 影格有哪些合成物件？其世界位置與像素位置為何？」寫出查詢應讀取的資料、驗證步驟，以及答案中應附上的來源資訊。再說明它不能據此推論什麼。

## 習題解答

### 解答一

影格時間為

$$
t_7=\frac{7}{10}=0.7\ \text{秒}.
$$

像素欄索引為

$$
u=\operatorname{round}
\left(\frac{0.25-(-1)}{1-(-1)}(21-1)\right)
=\operatorname{round}(0.625\times20)
=\operatorname{round}(12.5).
$$

Python 的 `round` 對恰好位於兩整數中點的值採銀行家捨入，因此此例索引為12。若專案需要另一種取整規則，例如一律向下或四捨五入遠離零，必須明確定義並在生成器與測試中統一使用。

### 解答二

至少可測：

1. 第0影格時間仍為 \(0/2=0\) 秒，第7影格為 \(7/2=3.5\) 秒。
2. manifest列出8個影格，索引為0至7，且時間皆等於 `frame_index / FPS`。
3. 每個manifest項目的影像與標註路徑都對應存在於生成流程預期的命名規則中；若以實際檔案檢查，應由讀者在本機執行後驗證。
4. 若同時修改 `FRAME_COUNT` 與 `FPS`，影像尺寸、色彩值域及物件ID測試仍應成立。

### 解答三

單一影像通常無法唯一還原三維世界位置；相機投影會丟失深度，圓點顏色也只表示程式繪製的標記。檔名沒有時間與資料集識別碼，不能確認它屬於哪一次生成；也沒有標註路徑可查到ID與世界座標。

至少應補上資料集ID、影格編號、時間與時間單位、生成設定或版本識別、影像路徑、標註路徑，以及標註中的穩定物件ID、世界位置及其座標系和單位、像素位置與像素原點約定、資料來源狀態。

### 解答四

查詢先讀取manifest，確認資料集ID、影格編號與標註路徑；再讀取該影格JSON，檢查影格編號和時間與manifest一致。對每筆物件標註，確認來源標記為合成，並讀出穩定物件ID、世界座標、像素座標及其單位與座標約定。回答應附資料集ID、影格編號、時間、標註檔名及使用欄位。

此查詢只能整理記錄中的合成狀態，不能推論現場魚數、真實位置、健康狀態、生態行為或設備感測結果；它也不應控制池體設備或改寫資料。

## 本章小結

可稽核的數位分身專題，需讓場景、動畫、影像、標註與清單共享一致的影格編號、時間及物件ID，並明示單位、座標系與資料來源。本章以固定時間步生成合成影像序列和JSON標註，再由manifest追溯每個輸出；程式示範的是資料流程，不是完整三維渲染器。唯讀查詢應引用具體資料欄位，遇到資料未提供的問題就明確指出缺漏。合成結果不等於實測，也不構成生物、物理或養殖控制驗證。
