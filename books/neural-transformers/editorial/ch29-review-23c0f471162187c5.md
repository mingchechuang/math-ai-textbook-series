## 總評

本輪提供的章稿與前輪仍是同一實質版本；我重新沿目前程式控制流、Python 型別規則、Schema reduction、重試次數及事件序列核對。主體架構已接近可接受：模型提議不直接執行；allowlist、角色與 Schema 由程式端控制；handler 限於本機記憶體 mock；不存在 shell、網路或設備操作；`call_id` 固定；`max_retries` 的語義清楚；輸入與結果使用 canonical JSON 摘要；命題也將受保護狀態和稽核狀態分開。

然而，本輪仍未修正前稿中兩項確定錯誤：

1. 習題 2 解答聲稱存在工具名稱前綴拒絕，主程式實際沒有該功能。

此外，重試事件仍漏記暫時失敗，若干已實作的安全分支沒有故障測試，Schema 註冊期檢查仍可能被不一致型別破壞。這些涉及自足程式、完整解答與故障測試，不是可略過的風格意見。

## 一、阻擋核准：習題 2 的安全機制說明與程式相反

### 逐字原句

> `# set_alert_threshold 不註冊，因為它包含寫入操作，且名稱不以 get/read/query 開頭會被 register_tool 拒絕`

### 重算

目前 `register_tool()` 只檢查：

```python
if not isinstance(tool_name, str) or not tool_name:
    ...
if tool_name in self.tools:
    ...
```

沒有任何 `startswith("get_")`、`startswith("read_")` 或 `startswith("query_")`。

因此以下註冊會成功，而不是被名稱拒絕：

```python
gateway.register_tool(
    "set_alert_threshold",
    {},
    ["admin"],
    lambda p: {"ok": True}
)
```

只要呼叫者是受信任初始化程式，此工具就會進入 `self.tools`。此事也再次證明名稱本身不能建立唯讀性。

### 最小修法

不要恢復脆弱的名稱前綴規則；只改答案文字：

> `set_alert_threshold` 不在受信任初始化程式建立的固定 allowlist 中，因此所有角色皆拒絕。模型與一般使用者不能呼叫 `register_tool()`；名稱不構成唯讀證明。

題目名為「權限矩陣」，答案還應明列：

| 工具 | monitor | analyst | admin |
|---|---:|---:|---:|
| `get_sensor_data` | Allow | Allow | Allow |
| `get_historical_report` | Deny | Allow | Allow |
| `render_export_preview` | Deny | Deny | Allow |
| `set_alert_threshold` | Deny | Deny | Deny |

## 二、阻擋核准：習題 3 的替代驗證與 `^a+$` 不等價

### 逐字原句

```python
def is_safe_a_string(s):
    return all(c == 'a' for c in s)
```

正文稱它是 `^a+$` 的安全替代。

### 原因

Python 對空 iterable 的 `all()` 回傳 True，所以：

```python
is_safe_a_string("")
```

結果是 True。

但 `^a+$` 中的 `+` 表示至少一個 `a`，空字串必須失敗。答案因此有確定的邊界錯誤。

此外，若傳入非字串 iterable，例如 `[]`，函數也會因空 iterable 回傳 True，與「僅允許由 `a` 組成的字符串」不符。

### 最小修法

```python
def is_safe_a_string(s):
    return (
        isinstance(s, str)
        and len(s) > 0
        and all(c == "a" for c in s)
    )
```

並補預期測試：

```python
assert is_safe_a_string("aaa") is True
assert is_safe_a_string("") is False
assert is_safe_a_string("aa!") is False
assert is_safe_a_string([]) is False
```

## 三、狀態機仍漏記真正的重試原因

### 逐字原句

```python
except TransientReadError as e:
    attempts += 1
    if attempts <= max_retries:
        continue
```

習題 5 所列事件為：

> `RECEIVED`, `VALIDATED`, `EXECUTING`(1), `EXECUTING`(2), `SUCCEEDED`

### 重新推算

第一次 handler 拋出 `TransientReadError` 時，沒有任何事件被寫入。日誌直接從：

```text
EXECUTING attempt=1
```

跳到：

```text
EXECUTING attempt=2
```

這只能讓人推測前次執行失敗，不能直接核對：

- 前次是暫時性失敗；
- Gateway 決定重試；
- 哪一個 attempt 失敗；
- 是否因重試上限而終止。

本章核心包含「狀態與失敗重試」，所以不能只記執行次數而略去失敗轉移。

### 最小修法

新增：

```python
ATTEMPT_FAILED = "ATTEMPT_FAILED"
```

在捕捉暫時錯誤後記錄：

```python
attempts += 1
will_retry = attempts <= max_retries
self.logger.log(
    EventStatus.ATTEMPT_FAILED,
    tool_name,
    {
        "attempt": attempts,
        "reason_code": "TRANSIENT_READ_ERROR",
        "will_retry": will_retry
    },
    call_id
)
```

若 `will_retry` 為 False，再記最終 `FAILED` 或直接讓該 `ATTEMPT_FAILED` 成為終態；兩種均可，但習題、正文及程式必須一致。

## 四、失敗事件的欄位契約不一致

### 逐字原句

```python
{"error": "result not JSON-serializable"}
```

```python
{"error": "Max retries exceeded"}
```

```python
{"exception_type": type(e).__name__}
```

### 原因

三者都使用 `EventStatus.FAILED`，卻沒有共同的機器可讀原因碼。稽核程式只能解析自由文字或猜測欄位存在與否。

### 最小修法

統一加入：

```python
{"reason_code": "INVALID_TOOL_RESULT"}
```

```python
{"reason_code": "RETRY_EXHAUSTED"}
```

```python
{
    "reason_code": "HANDLER_EXCEPTION",
    "exception_type": type(e).__name__
}
```

對外 API 的 `code` 不必改動。

## 五、主程式已有重要故障分支，測試卻未覆蓋

### 1. `INVALID_PARAMS_ENCODING`

**原句：**

```python
except (TypeError, ValueError):
    ...
    return {
        "status": "error",
        "code": "INVALID_PARAMS_ENCODING",
        ...
    }
```

目前沒有測試觸發它。

**最小故障測試：**

```python
before = HANDLER_CALL_COUNT
result = gateway.execute_tool_call({
    "tool": "get_ph_level",
    "params": {"sensor_id": {"PH-01"}}
})
assert result["status"] == "error"
assert result["code"] == "INVALID_PARAMS_ENCODING"
assert HANDLER_CALL_COUNT == before
```

set 不能 JSON 序列化，因此應在 handler 前拒絕。

---

### 2. `INVALID_TOOL_RESULT`

**原句：**

```python
return {
    "status": "error",
    "code": "INVALID_TOOL_RESULT",
    ...
}
```

沒有 handler 回傳 set 或其他不可序列化結果的測試。

**最小修法：**

建立：

```python
def bad_result_handler(params):
    return {"values": {1, 2}}
```

核對：

- handler 確實被調用；
- Gateway 回 `INVALID_TOOL_RESULT`；
- 同一 `call_id` 有 `FAILED`；
- 同一 `call_id` 沒有 `SUCCEEDED`；
- hash chain 仍是預期有效。

---

### 3. 控制鍵注入

程式明確定義：

```python
control_keys = {"required"}
```

但沒有測試模型把 `"required"` 放入 params。

**最小測試：**

```python
before = HANDLER_CALL_COUNT
result = gateway.execute_tool_call(json.dumps({
    "tool": "get_ph_level",
    "params": {
        "sensor_id": "PH-01",
        "required": []
    }
}))
assert result["code"] == "SCHEMA_VIOLATION"
assert HANDLER_CALL_COUNT == before
```

---

### 4. 同名註冊覆寫

程式明確拒絕：

```python
if tool_name in self.tools:
    raise ValueError(...)
```

但沒有測試。這是防止啟動期誤覆寫受信任 handler 的重要故障案例。

**最小修法：**

補一個預期拋出 `ValueError` 的測試，並核對原 handler 仍存在。

## 六、Schema 註冊期檢查仍有型別問題

### 1. `min` 與 `max` 可在註冊時產生 TypeError

**原句：**

```python
if min_val is not None and max_val is not None and min_val > max_val:
```

例如：

```python
{"x": {"type": "int", "min": "1", "max": 10}}
```

字串與整數不可比較，會拋 `TypeError`，而不是清楚的 `ValueError`。

**最小修法：**

依欄位 `type` 先驗證邊界型別，再比較大小；int 邊界必須用 `type(v) is int` 排除 bool，float 邊界必須有限。

---

### 2. Enum 元素沒有依欄位型別核對

以下 schema 可成功註冊：

```python
{"x": {"type": "int", "enum": [1, True, "2"]}}
```

`True == 1` 又會造成 membership 語義混淆。

**最小修法：**

逐個驗證 enum 元素：

- str 只接受字串；
- int 使用 `type(v) is int`；
- float 接受非 bool 的有限 int/float。

---

### 3. `max_length` 沒有驗證

`max_length=True` 會等同 1；負數會拒絕所有非空字串；字串型上限會在執行期比較失敗。

**最小修法：**

註冊時要求：

```python
type(max_length) is int and max_length >= 0
```

---

### 4. 角色元素沒有驗證

**原句：**

```python
set(allowed_roles)
```

若元素是 list，會拋 `TypeError`；若元素是整數，則會被接受但不符合角色字串契約。

**最小修法：**

要求所有角色都是非空字串。

---

## 七、參數域定義與實作不一致

### 逐字原句

> 字串必須匹配正規表達式且長度 $\le L_{max}$。

### 實作

只有存在 `max_length` 時才檢查：

```python
if max_len is not None and len(value) > max_len:
```

而習題 2 使用：

```python
{"sensor_id": {"type": "str"}}
```

既無 pattern，也無 `max_length`。

### 最小修法

二選一：

1. 對所有字串欄位強制要求有限 `max_length`；或
2. 將正文改成「字串可由完整 pattern 及／或 `max_length` 限制」。

本章以不可信模型輸入為主，較建議第一種。

## 八、稽核鏈實作仍有一致性缺口

### 1. 事件序列化未使用 `allow_nan=False`

**原句：**

```python
json.dumps(
    event_dict,
    sort_keys=True,
    separators=(",", ":")
)
```

參數與結果均拒絕 NaN/Infinity，事件卻沒有採用相同規則。

**最小修法：**

加入：

```python
allow_nan=False
```

---

### 2. `event_seq` 在序列化成功前先增加

**原句：**

```python
self.event_seq += 1
event_body = {...}
payload = self._serialize_event(event_body)
```

若序列化失敗，事件沒有 append，但計數已增加；下一筆成功事件產生序號缺口。

**最小修法：**

先計算 `next_seq = self.event_seq + 1`，成功建立 entry 並 append 後才提交 `self.event_seq = next_seq`。

---

### 3. `verify_chain()` 不核對事件序號連續性

目前只核對 prev hash 與事件 hash，沒有核對：

```python
entry["event"]["event_seq"] == i + 1
```

**最小修法：**

增加事件序號檢查，並核對：

```python
self.event_seq == len(self.events)
```

這不會解決整鏈重寫或尾端截斷；正文已正確說明那些不在此 mock 的保證範圍。

## 九、命題與實作副作用的邊界

### 1. Handler 寫入全域測試計數器

**原句：**

> 被註冊的工具實現本身是封閉且可信的，且不具備寫入或網路能力

但 handler 執行：

```python
global HANDLER_CALL_COUNT
HANDLER_CALL_COUNT += 1
```

這是記憶體寫入。若它只屬於測試 instrumentation 且不屬於 $S_{\text{protected}}$，命題仍成立，但必須明示。

**最小修法：**

補充：

> `HANDLER_CALL_COUNT` 是測試觀測狀態，不屬於受保護業務狀態；正式唯讀 handler 不含此計數副作用。

---

### 2. 無效提議也應有保持性推論

命題只寫「系統僅執行有效調用」，但本章大部分安全測試是無效提議。它們不執行 handler，只追加 `DENIED`。

**最小修法：**

補一個推論：

> 無效提議不會進入 handler，因此 $S_{\text{protected}}$ 不變；只向 $S_{\text{audit}}$ 追加拒絕事件。

## 十、例題、案例與能力聲稱

### 1. 例題一返回值少了 `ok`

**原句：**

> 返回 `{"error": "Sensor not found"}`

實作為：

```python
{"ok": False, "error": "Sensor not found"}
```

應逐字同步。

---

### 2. 兩個 hash 不是彼此匹配

**原句：**

> 驗證 `details` 中的參數哈希與工具返回值哈希是否匹配

參數與結果內容不同，摘要通常不相等。

**最小修法：**

改成：

> 分別以相同 canonical JSON 規則重算另行保存的原始參數及結果，核對 `RECEIVED.details.params_hash` 與 `SUCCEEDED.details.result_hash`。

---

### 3. 小結把稽核能力寫得過強

**原句：**

> 可檢測竄改的稽核日誌

章首已正確限定只能檢測「未同步重算之部分修改」。

**最小修法：**

小結沿用完整限定，不能重新概括成一般不可竄改或全面可檢測。

---

### 4. 「確保操作唯讀」仍是條件性能力

Gateway 不會分析 handler 的檔案、網路或設備能力；唯讀性來自受信任註冊前提。

**最小修法：**

將：

> 確保操作是唯讀的

改成：

> 只允許受信任初始化程式預先註冊的唯讀 mock handler；Gateway 不由工具名稱推導唯讀性。
