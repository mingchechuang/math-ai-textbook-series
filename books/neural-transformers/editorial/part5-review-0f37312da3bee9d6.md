現稿仍有以下需要局部修正的實質問題。

### 1. 第26章把輸出通道誤稱為「每一行」，與全卷row／column約定相反

**逐字原句：**「若把同一條公式套到矩陣 $W\in\mathbb{R}^{D_{\mathrm{in}}\times D_{\mathrm{out}}}$ 的每一行（輸出通道）上，$s$ 就是形狀 $(D_{\mathrm{out}},)$ 的向量……要沿第 0 軸（$D_{\mathrm{in}}$）取 $\max$。」

**重算與原因：** 在本卷$Y=XW$約定下，$W$的第$j$個**column**包含輸出通道$j$的$D_{\mathrm{in}}$個權重。沿第0軸取最大，對固定$j$得到$\max_i|W_{ij}|$；整體尺度為$(D_{\mathrm{out}},)$，或程式保留維度後的$(1,D_{\mathrm{out}})$。若真的「每一行」各給一個尺度，就應沿第1軸reduction，shape應為$(D_{\mathrm{in}},1)$。現有`quantize_per_column`及習題B1的兩個**程式軸**反而正確，錯在正文把column說成row，令跨章座標術語自相矛盾。

**最小修法：** 把「每一行（輸出通道）」改為「每一欄（輸出通道）」；說明尺度在程式中以`keepdims=True`保留為$(1,D_{\mathrm{out}})$。無須把現有`axis=0`改掉，也不應把習題B1的逐列版本誤稱逐輸出通道。

### 2. 第26章只驗證`bits>=2`，卻直接把任意大位元數量化碼轉成`int64`

**逐字原句：**「`if type(bits) is not int or bits < 2: raise ValueError(...)`」；兩個量化函式其後均以「`np.clip(np.round(...), -qmax, qmax).astype(np.int64)`」輸出碼。

**重算與原因：** $q_{\max}=2^{b-1}-1$。在$b=65$時，$q_{\max}=2^{64}-1$，已大於有號`int64`的最大值$2^{63}-1$。對例如$x=[1]$，量化碼在數學上可到$q_{\max}$，但所選儲存dtype不能表示；在更大$b$時尺度計算亦可能下溢。命題26.1的實數算術誤差界，不能保證這段有限精度程式在所有「至少2的整數」上有效。位元數上限目前沒有定義，故函式接受了與其輸出dtype不相容的輸入。

**最小修法：** 對教學程式明定並檢查所支持的位元數，例如僅支持章內實際討論的$2\le b\le8$；若要支持更大範圍，至少使$q_{\max}$落在`int64`可表示範圍，並另處理尺度下溢。補一項超出上限的故障測試。此修法不改變三、四、八位元手算。

### 3. 第26章縮放後有限，仍不足以保證KL回傳值有限；程式與數值策略須一致

**逐字原句：**「`softmax_temp` 會拒絕非有限輸入及非有限的 `z/T`，但有限的縮放 logits 相減仍可能在極端數值下溢出，故不可把 `np.where` 當作所有數值故障的防護。」

**相關程式原句：** `logp = st - logsumexp(st, axis=-1)`、`logq = ss - logsumexp(ss, axis=-1)`、`term = np.where(p > 0, p * (logp - logq), 0.0)`，隨後直接回傳`loss, grad`。

**重算與原因：** 修稿已準確承認尚有失效路徑，但函式本身沒有依本卷「非有限logits／loss需定義策略」攔截它。例如一列縮放後學生logits為$[10^{308},-10^{308}]$：兩個元素個別有限，`logsumexp`約$10^{308}$，第二項相減的數學值為$-2\times10^{308}$，超出`float64`可表示範圍，成為`-inf`。若教師在第二類分配正質量，對應KL項可變成`+inf`；`np.where`不能令該正支撐項有限，也不該以任意epsilon偽裝精確。回傳非有限loss或梯度時，目前沒有明確拒絕或允許規則。

**最小修法：** 在計算`logp`、`logq`、逐樣本KL、總loss及梯度後按契約作有限性檢查，不能表示時以明確例外拒絕；另加「縮放後仍有限、但相減溢位」的故障測試。若選擇容許數學上的$+\infty$ KL，則要明訂何時回傳無窮、梯度如何處理及訓練是否中止；不應靜默傳入後續訓練。

### 4. 第27章仍聲稱有「摘要頁取得紀錄」，但現稿未提供該紀錄

**逐字原句：**「目前僅有摘要頁取得紀錄，本文不宣稱已完整核對論文。」第27章參考來源第1、2項均使用此說法。

**原因：** 可定位的論文網址和「未完整核對」是合適的來源範圍聲明；「有摘要頁取得紀錄」則另行聲稱存在一次取得行為及其紀錄。提交內容沒有提供該紀錄，本審稿亦不能代作者確認。第26章已將同類表述修為「背景入口；未完整閱讀」，因此兩章在來源能力聲明上尚未一致。這不是要求刪除Vaswani或Hu論文，也不是判定網址錯誤。

**最小修法：** 如沒有可交付的取得紀錄，把兩處「目前僅有摘要頁取得紀錄」改為「背景入口；未完整核對」等不主張已取得頁面的文字。保留作品資訊與網址。

### 5. 第30章「窗口」手算與實際`make_windows`建立方式不同

**逐字原句：**「若某train文件token索引為0至6，可建立索引0–3、1–4、2–5、3–6的重疊視窗，但它們全屬同一來源文件與train集合。」

**相關程式原句：** `for start in range(0, len(ids) - 1, context):`。

**重算與原因：** 手算所列長度4窗口起點依序是0、1、2、3，即步長1的重疊視窗；程式以`context`為步長。當`context=4`，起點為0、4等，而非0、1、2、3。程式仍能形成合法的位移next-token訓練對，也仍按文件group切分；但它不是正文與陷阱段落屢次提及的「同一文件相鄰視窗高度重疊」之實作。這會混淆讀者對資料量、token計數及洩漏測試範圍的預期。

**最小修法：** 二選一：若專題要展示重疊視窗，將步長明定為1並維持每個窗口輸入／標籤的位移；若要保留目前不重疊的分塊實作，將手算例註明為「可採用的另一種建窗方案」，並把描述實際程式窗口為高度重疊的句子改為分塊。group先切後建窗的正確順序不需改。

### 6. 第30章對「來源不符」的拒答範圍已限縮，但測試清單仍寫得較廣

**逐字原句：**「**不存在來源**：mock工具沒有指定文件或可核對span時，預期Agent拒答。」

**相關程式原句：** `if cited_doc_id is None`時拒答；其後只以`if hit["doc_id"] == cited_doc_id`接受命中。

**原因：** 章首現已清楚限定本基線只回傳當次lookup的命中片段，不做版本化逐字引用核驗，這一修正可接受。可是上述故障測試中的「或可核對span時」仍暗示對span本身做獨立核對；實作沒有這個分支，也沒有錯終點、錯span、錯版本的注入測試。正常mock生成的span原本從文字切出，因此正常命中有位置，不能據此推論已測到偽造span被拒絕。

**最小修法：** 若保留現有簡化基線，把該項改寫為「未指定`cited_doc_id`，或指定doc_id不在當次命中中時拒答；尚未測偽造span及版本」，與章首及「Cache、資料與工具契約」一致。若欲保留「可核對span時拒答」作為已實作預期，就需增加獨立覆核和相應故障注入。
