## 一、阻擋項：習題 2 仍聲稱不存在的名稱前綴規則

### 逐字原句

> `# set_alert_threshold 不註冊，因為它包含寫入操作，且名稱不以 get/read/query 開頭會被 register_tool 拒絕`

### 自行重算

`register_tool()` 的名稱檢查只有：

```python
if not isinstance(tool_name, str) or not tool_name:
    raise ValueError(...)
if tool_name in self.tools:
    raise ValueError(...)
```

沒有 `startswith()`、正則或前綴 allowlist。因此下面的註冊依目前程式會成功：

```python
gateway.register_tool(
    "set_alert_threshold",
    {},
    ["admin"],
    lambda p: {"ok": True}
)
```

### 原因

這是虛構了 `register_tool()` 不具備的能力。工具名稱本身也不能證明唯讀性：`get_x` 可能寫檔，`render_x` 可能純粹回傳記憶體結果。前文正確的安全模型是「模型與一般使用者不能註冊工具，受信任初始化程式只建立固定 allowlist」，解答卻改成名稱前綴防護，兩者矛盾。

### 最小修法

將註解改為：

> `set_alert_threshold` 不在受信任初始化程式建立的固定 allowlist 中，因此所有角色均拒絕；模型與一般使用者不能接觸 `register_tool()`。工具名稱本身不是唯讀證明。

題目要求權限矩陣，答案也應明列：

| 工具 | monitor | analyst | admin |
|---|---:|---:|---:|
| `get_sensor_data` | Allow | Allow | Allow |
| `get_historical_report` | Deny | Allow | Allow |
| `render_export_preview` | Deny | Deny | Allow |
| `set_alert_threshold` | Deny | Deny | Deny |

只改這段註解與補表格即可，不應新增名稱前綴規則。

## 二、每次暫時性失敗仍沒有事件紀錄

### 逐字原句

```python
except TransientReadError as e:
    # 暫時性錯誤，重試
    attempts += 1
    if attempts <= max_retries:
        continue
```

### 自行重算成功重試事件

第一次失敗、第二次成功時，目前事件依序為：

1. `RECEIVED`
2. `VALIDATED`
3. `EXECUTING`, attempt 1
4. `EXECUTING`, attempt 2
5. `SUCCEEDED`

其中沒有任何事件明確表示 attempt 1 發生暫時性失敗。稽核者只能從第二個 `EXECUTING` 推測前一次未成功，無法由事件直接確認失敗原因與是否決定重試。

### 最小修法

加入：

```python
ATTEMPT_FAILED = "ATTEMPT_FAILED"
```

並在捕捉後記錄：

```python
attempts += 1
will_retry = attempts <= max_retries
self.logger.log(
    EventStatus.ATTEMPT_FAILED,
    tool_name,
    {
        "attempt": attempts,
        "reason_code": "TRANSIENT_READ_ERROR",
        "will_retry": will_retry
    },
    call_id
)
```

不要記錄原始例外文字。習題 5 的成功序列應同步改為：

```text
RECEIVED
VALIDATED
EXECUTING(1)
ATTEMPT_FAILED(1, will_retry=True)
EXECUTING(2)
SUCCEEDED
```

`max_retries=2` 且連續失敗時，總 handler 呼叫次數仍是三次，現有迴圈在這一點沒有 off-by-one 錯誤。

## 三、`FAILED` 事件 details 尚無共同契約

### 逐字原句

結果不可序列化：

```python
{"error": "result not JSON-serializable"}
```

重試耗盡：

```python
{"error": "Max retries exceeded"}
```

其他 handler 例外：

```python
{"exception_type": type(e).__name__}
```

### 原因

三種事件狀態均為 `FAILED`，但 details 沒有共同的機器可讀分類欄位。後續稽核程式只能解析英文文字或依欄位名稱猜測原因。

### 最小修法

所有 `FAILED` details 加入 `reason_code`：

```python
{"reason_code": "INVALID_TOOL_RESULT"}
{"reason_code": "RETRY_EXHAUSTED"}
{"reason_code": "HANDLER_EXCEPTION",
 "exception_type": type(e).__name__}
```

對外回傳碼不必更改。

同理，`DENIED` 事件目前也分別使用 `error`、`reason`、`role` 等不同結構。若不打算全面統一，至少應讓所有拒絕事件都帶對外錯誤碼相同的 `reason_code`，例如 `TOOL_NOT_FOUND`、`PERMISSION_DENIED`、`SCHEMA_VIOLATION`。

## 四、Schema 註冊期驗證不完整

### 4.1 `min`／`max` 型別可能直接觸發 TypeError

### 逐字原句

```python
if min_val is not None and max_val is not None and min_val > max_val:
```

例如：

```python
{"x": {"type": "int", "min": "1", "max": 10}}
```

會比較字串與整數並拋 `TypeError`，而不是受控 `ValueError`。

### 最小修法

比較前依欄位型別驗證上下界：

- `int`：`type(bound) is int`；
- `float`：非 bool 的 int/float 且有限；
- `str`：拒絕 `min`／`max`，除非另行定義其語義。

只設定單邊界時也必須驗證；目前程式只有兩者皆存在時才比較，單獨的錯型邊界會留到調用期才造成錯誤。

---

### 4.2 Enum 元素未按欄位型別驗證

以下 schema 能通過註冊：

```python
{"x": {"type": "int", "enum": [1, True, "2"]}}
```

Python 中 `True == 1`，共同位置的：

```python
value not in enum_vals
```

不能代替精確型別檢查。

### 最小修法

註冊時逐個驗證 enum 元素。整數 enum 使用 `type(v) is int`；float enum 排除 bool 並要求有限；字串 enum 要求實際字串。

---

### 4.3 `max_length` 未驗證

目前 `max_length=True` 會被視為 1；負值會拒絕全部非空字串；字串值則可能在：

```python
len(value) > max_len
```

拋 `TypeError`。

### 最小修法

註冊時要求：

```python
type(max_len) is int and max_len >= 0
```

且只允許字串欄位使用。

---

### 4.4 角色元素未驗證

`allowed_roles` 雖要求 list／tuple／set，但元素可能是整數、空字串或 list。含 list 時：

```python
set(allowed_roles)
```

會拋 `TypeError`。

### 最小修法

建立 set 前要求每個角色均為非空字串。

---

### 4.5 未限制未知的 Schema 控制鍵

欄位定義可以包含拼錯的：

```python
{"type": "str", "max_lenght": 10}
```

註冊時不會拒絕，執行時該限制會被靜默忽略。

### 最小修法

依型別建立允許的 field-definition key 集合，例如：

- str：`type`, `pattern`, `max_length`, `enum`
- int/float：`type`, `min`, `max`, `enum`

遇到其他鍵立即 `ValueError`。

## 五、字串受限域的定義與實作不一致

### 逐字原句

> 字串必須匹配正規表達式且長度 $\le L_{max}$。

但主工具只有 pattern，沒有 `max_length`；習題 2 更使用：

```python
{"sensor_id": {"type": "str"}}
```

既沒有 pattern，也沒有最大長度。

### 最小修法

二選一：

1. 在 `register_tool()` 強制每個字串 schema 都有非負 `max_length`，pattern 則視需求選用；或
2. 把正文「必須匹配正規表達式且長度……」改為「可由 pattern 與最大長度約束」。

考慮本章處理模型生成的不可信輸入及 ReDoS，至少應強制有限 `max_length`。主工具的 `sensor_id` 可加一個足以容納固定格式的有限長度。

## 六、AuditLogger 仍有一致性缺口

### 6.1 事件序列化未拒絕 NaN

### 逐字原句

```python
return json.dumps(
    event_dict,
    sort_keys=True,
    separators=(",", ":")
).encode("utf-8")
```

參數與結果都使用 `allow_nan=False`，事件卻沒有。若 details 出現 `float("nan")`，Python 預設可輸出非標準 JSON 的 `NaN`。

### 最小修法

加入：

```python
allow_nan=False
```

---

### 6.2 `event_seq` 在事件成功建立前遞增

### 逐字原句

```python
self.event_seq += 1
...
payload = self._serialize_event(event_body)
```

若序列化失敗，事件沒有 append，但計數器已增加，下一筆事件產生序號空洞。

### 最小修法

使用候選序號：

```python
next_seq = self.event_seq + 1
```

成功序列化、計算 hash 並 append 後，再提交：

```python
self.event_seq = next_seq
```

---

### 6.3 `verify_chain()` 未核對序號

目前只檢查 `prev_hash` 與事件內容 hash，沒有檢查：

```python
entry["event"]["event_seq"] == i + 1
```

也沒有核對：

```python
self.event_seq == len(self.events)
```

### 最小修法

加入上述兩項。這仍然不能防止攻擊者重算整條鏈或截斷尾端；章首對能力限制的說明是正確的。

---

### 6.4 驗證遇到非法事件可能拋例外而非返回 False

若事件被改成含不可序列化值，或 entry 缺少 `event`、`hash`、`prev_hash`，目前 `verify_chain()` 可能拋 `TypeError`／`KeyError`。

### 最小修法

在驗證函數內將結構與序列化錯誤轉為 `False`。這屬於驗證不可信日誌副本時較穩健的行為。

## 七、故障測試仍未覆蓋新增安全分支

目前已有正常、邊界與多種拒絕測試，但以下分支沒有測試。

### 7.1 `INVALID_PARAMS_ENCODING`

```python
before = HANDLER_CALL_COUNT
result = gateway.execute_tool_call({
    "tool": "get_ph_level",
    "params": {"sensor_id": {"PH-01"}}
})
assert result["code"] == "INVALID_PARAMS_ENCODING"
assert HANDLER_CALL_COUNT == before
```

### 7.2 `INVALID_TOOL_RESULT`

註冊返回 set 的 handler：

```python
def bad_result_handler(params):
    return {"values": {1, 2}}
```

核對：

- 返回 `INVALID_TOOL_RESULT`；
- 同一 `call_id` 有 `FAILED`；
- 沒有 `SUCCEEDED`；
- 稽核鏈仍可驗證。

### 7.3 控制鍵注入

```python
{
    "tool": "get_ph_level",
    "params": {
        "sensor_id": "PH-01",
        "required": []
    }
}
```

預期 `SCHEMA_VIOLATION`，handler 呼叫次數不變。

### 7.4 同名工具重複註冊

確認第二次註冊相同名稱拋 `ValueError`，原 handler 未被覆寫。

### 7.5 非有限 float schema／enum

補一個註冊期測試，確保 `float("nan")` 或 `float("inf")` 不可作為上下界或 enum 元素。

這些是小型故障測試，不需擴寫整個測試框架。

## 八、測試 instrumentation 與唯讀命題的邊界

### 逐字原句

> 被註冊的工具實現本身是封閉且可信的，且不具備寫入或網路能力

但兩個 handler 都執行：

```python
HANDLER_CALL_COUNT += 1
```

這是共享記憶體寫入。它沒有修改 `MOCK_SENSOR_DATA`，因此不會推翻只保證 $S_{\text{protected}}$ 不變的命題；但稿件必須明示其分類。

### 最小修法

補充：

> `HANDLER_CALL_COUNT` 是測試 instrumentation，屬於測試觀測狀態，不屬於受保護業務狀態；正式唯讀 handler 不包含此計數副作用。

## 九、稽核摘要說明仍有語義錯誤

### 逐字原句

> 驗證 `details` 中的參數哈希與工具返回值哈希是否匹配（需與另行保存的結果重算比較）。

`params_hash` 和 `result_hash` 是不同內容的摘要，通常不應彼此相等。

### 最小修法

改為：

> 對另行保存的原始參數與結果分別使用相同 canonical JSON 規則重算摘要，再分別核對日誌中的 `params_hash` 與 `result_hash`。

另需注意，現有 logger 把參數 hash 記在 `RECEIVED`、結果 hash 記在 `SUCCEEDED`，不在同一筆 `details` 中；文字應說「對應事件的 details」，不要暗示兩者在同一事件。

## 十、能力措辭仍過強

### 逐字原句一

> 確保操作是唯讀的（Read-Only）。

Gateway 本身沒有靜態分析、能力沙箱或系統呼叫攔截；它只信任預先註冊的 handler。

### 最小修法

改成：

> 只允許受信任初始化程式預先註冊的唯讀 mock handler；Gateway 不從名稱推導或獨立證明 handler 唯讀。

### 逐字原句二

> 可檢測竄改的稽核日誌

章首已較精確地限定為「可檢測未同步重算之部分修改」。小結應沿用同一限制：

> 可檢測未同步重算之部分修改的教學用雜湊鏈日誌。

### 逐字原句三

> 這種設計在特定假設下確保了AI系統僅作為輔助監控工具，而不具備破壞性或控制性能力

本例確實沒有控制工具，但 Gateway 類本身可以被受信任程式註冊任意 callable；安全性來自部署時的能力隔離與固定註冊表，而非該類在語言層阻止副作用。

### 最小修法

改成：

> 在本章封閉 mock、固定 allowlist、模型不能註冊工具且程序不具外部能力的假設下，本例只執行輔助監控查詢。
