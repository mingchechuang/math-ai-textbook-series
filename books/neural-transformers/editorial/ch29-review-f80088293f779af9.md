## 總評

本章方向符合章綱：明確區分模型提議與程式授權，提供記憶體內的唯讀 mock、allowlist、參數驗證、角色檢查及事件紀錄，也沒有下載模型、連網、執行 shell 或控制設備。正文亦沒有宣稱程式已實際執行，測試多使用「預期」，這點合格。

但目前不能核准。主要問題不是文風，而是安全性定義與程式實作之間有數項實質矛盾：

1. 工具是否唯讀只靠名稱黑名單判定，任意有副作用的 handler 仍可註冊，因此核心安全保證不成立。
2. 「所有可寫狀態保持不變」的命題忽略稽核日誌本身必然寫入，也混淆純函數、唯讀資料查詢及受控稽核副作用。
3. Schema 缺少數值範圍、字串長度、optional/required、enum及跨欄位約束；負 limit 已由正文自己的習題暴露，卻沒有修正主程式。
4. Python 的 `bool` 是 `int` 子類，現有型別檢查會接受 `True` 作為 `limit`。
5. 稽核雜湊不是完整性保護，且習題的雜湊鏈程式存在 `str + bytes` 的確定型別錯誤，不能運行。
6. 章綱要求的狀態與失敗重試未完整實作；目前沒有 call ID、明確狀態機、重試分類、次數上限或冪等語義。
7. 有數處過度保證、未支持的來源條目，以及未完成的故障測試。

以下先依定義及程式逐項重算，再給最小修法。

## 一、阻擋核准的正確性與安全問題

### 1. 工具名稱檢查不能證明 handler 唯讀

**原句：**

> `if not self._is_read_only_tool(tool_name):`  
> `    raise ValueError(f"Tool {tool_name} is not marked as read-only")`

以及：

> `# 簡單檢查：工具名不能包含 write, set, delete, create, update`

以及：

> `handler_func: 實際執行函數，必須保證唯讀`

**原因：**

這裡只檢查名稱，不檢查能力。名為 `get_sensor_data` 的函數完全可以寫檔、修改全域變數、開 socket、啟動 subprocess 或操作設備；相反，名稱中含有 `dataset` 的安全讀取工具會因包含子字串 `set` 而被誤拒絕。逐字串檢查既有假陰性，也有假陽性。

例如 `dataset_lookup` 包含 `"set"`，會被拒絕；但以下 handler 名稱可通過，卻有寫入副作用：

```python
def get_sensor_data(params):
    global counter
    counter += 1
    return {}
```

因此命題中的前提「所有被調用工具皆無副作用」並未由 Gateway 建立。把責任留給註冊者的文字約定，可以作為明示信任邊界，但不能稱為程式已確保唯讀。

**最小修法：**

不要把 `_is_read_only_tool` 描述為安全證明。改採固定程式碼內建的工具表，不提供接受任意 handler 的公開註冊介面，例如在建構子中直接建立：

```python
self.tools = {
    "get_dissolved_oxygen": {...},
    "get_ph_level": {...},
}
```

若保留 `register_tool`，必須明示它是「受信任啟動期管理介面」，模型與一般使用者不可接觸；名稱檢查只作輔助 lint，不是授權條件。由於本章要求的是記憶體 mock，最穩妥的最小修正就是只允許封閉的內建函數，不引入 shell、網路、檔案或任意 callback。

---

### 2. 唯讀性命題與稽核寫入互相矛盾

**原句：**

> 若系統中所有被調用的工具均滿足 $\sigma(t)=\emptyset$，且系統狀態僅由初始狀態與唯讀查詢結果決定，則系統在執行任意序列的有效調用後，其可寫狀態空間 $S_{write}$ 保持不變。

以及：

> `self.events.append(entry)`

**原因：**

每次調用都會向 `AuditLogger.events` 寫入，因此整個程式系統的可寫狀態顯然改變。若 $S_{write}$ 包含稽核狀態，命題是假；若不包含，正文必須把「受保護業務狀態」與「允許追加的稽核狀態」分開定義。

此外，「純函數或唯讀操作」也不是同義詞。查詢當前資料的唯讀函數可能因外部資料隨時間變動而不純；純函數則通常要求相同輸入得到相同輸出且無可觀察副作用。

**最小修法：**

將狀態寫成：

$$
S=(S_{\text{protected}},S_{\text{audit}})
$$

並將工具執行的保證改為：

$$
S'_{\text{protected}}=S_{\text{protected}},
$$

但允許：

$$
S'_{\text{audit}}=S_{\text{audit}}\mathbin{\|}e
$$

其中 $e$ 是追加事件。證明用歸納法：基底為零次調用；歸納步只證明受保護狀態不變，稽核序列追加一筆或多筆事件。這樣仍是一個完整小命題，且與程式一致。另將 $\sigma(t)=\emptyset$ 改成「對受保護資源的副作用集合為空」，不要聲稱整個程序無副作用。

---

### 3. 參數域不一定有限，複雜度陳述條件不足

**原句：**

> 我們定義參數空間 $\mathcal{P}$ 為有限離散集合的笛卡爾積。

以及：

> `timestamp` 必須屬於合法時間戳集合。

以及：

> 計算複雜度為 $O(|p|)$。

**原因：**

一般字串、整數與時間戳並不是有限集合，除非明確設定字串長度、整數上下界及時間範圍。主程式沒有字串長度限制，也沒有 `min`、`max` 或 `enum`，因此與定義不一致。

$O(|p|)$ 亦需說明 $|p|$ 是欄位數還是總輸入字元數。正則驗證的成本與字串長度及正則引擎行為有關；集合 membership 若用 list 是 $O(k)$，若用 hash set 才是平均 $O(1)$。不能一概稱為 $O(|p|)$。

**最小修法：**

將有限域改為「受限且可判定的參數域」，並要求每個字串有 `max_length`、整數有上下界。複雜度改稱：「對本章使用的線性正則及集合型 allowlist，驗證時間與輸入序列化長度近似線性；不對任意正則作此保證。」

---

### 4. Schema 不能表達正文所需的基本邊界

**原句：**

> Schema為字典，鍵為參數名，值為類型或正則表達式

主程式：

```python
"limit": {"type": "int"}
```

以及習題解答：

> `assert result["status"] == "error" or result["result"] == "ok" # 依實現而定`

**原因：**

`limit=-1` 在主程式會通過驗證，而 `data[-limit:]` 在 `limit=-1` 時等於 `data[1:]`，不是空列表，也不是錯誤。`limit=0` 時 `data[-0:]` 等於 `data[0:]`，反而返回全部資料。超大 limit 也未受限制。這不只是測試不完整，而是契約沒有定義關鍵範圍。

習題 5 的斷言幾乎允許任何結果，不能判定實作是否正確，也不屬於有效故障測試。

**最小修法：**

為 schema 加入 `minimum`、`maximum`，例如 `1 <= limit <= 100`，並在 `validate` 中實作。習題 5 必須固定預期為 Gateway 拒絕、handler 不被呼叫，並檢查 `DENY_SCHEMA_VIOLATION`。不能保留「依實現而定」。

---

### 5. `bool` 會被當成合法整數

**原句：**

```python
elif expected_type == 'int':
    if not isinstance(value, int):
        raise ToolContractError(...)
```

**原因：**

Python 中：

```python
isinstance(True, int)
```

為真。因此 `{"limit": True}` 通過契約，切片中 `True` 又可作為 1 使用。這是典型 schema 型別漏洞。

`float` 分支同樣接受布林值，因為 `bool` 也是 `int`。

**最小修法：**

改為：

```python
if type(value) is not int:
```

數值型則至少使用：

```python
if isinstance(value, bool) or not isinstance(value, (int, float)):
```

並補 `limit=True` 的故障測試。

---

### 6. 所有欄位都被當成必填，卻又宣稱 `limit` 有預設值

**原句：**

```python
limit = params.get("limit", 10)
```

但驗證器為：

```python
for key in self.schema.keys():
    if key not in params:
        raise ToolContractError(...)
```

**原因：**

依這個驗證器，schema 中每個欄位都是必填，因此 `params.get("limit", 10)` 的預設值永遠不會在通過 Gateway 的調用中生效。契約與 handler 語義不一致。

**最小修法：**

schema 明確加入 `required`，只檢查 required 欄位；或刪掉預設值並把 `limit` 明列必填。兩者擇一即可。若本章想展示 schema 契約，建議支援 `required: True/False`。

---

### 7. 雜湊鏈解答有確定的 Python 型別錯誤

**原句：**

```python
current_hash = hashlib.sha256(self.prev_hash + str(event).encode('utf-8')).hexdigest()
```

以及：

```python
hashlib.sha256(expected_prev + str(entry["event"]).encode('utf-8'))
```

**原因：**

`self.prev_hash` 與 `expected_prev` 是 `str`，後半段是 `bytes`，Python 不允許 `str + bytes`，會拋出 `TypeError`。因此習題解答不是可運行的自足程式。

此外，`str(dict)` 不適合作為穩定序列化契約；跨語言、不同資料型別或未來改動可能不一致。雜湊鏈只能檢測鏈內不一致；若攻擊者可改寫整份記憶體日誌，也能從被修改點重新計算後續所有雜湊。它不是不可竄改儲存。

**最小修法：**

先用固定 JSON 序列化，再整體編碼：

```python
payload = json.dumps(event, sort_keys=True, separators=(",", ":"))
material = (self.prev_hash + payload).encode("utf-8")
current_hash = hashlib.sha256(material).hexdigest()
```

驗證端完全採相同規則。文字上改稱「可檢查意外修改或不知道外部錨點的局部修改」，並說明真正抗重寫需要受保護的外部錨點、簽章或 append-only 儲存。本章不必實作外部服務。

---

### 8. 主稽核日誌中的 `hash` 不是事件完整性證明

**原句：**

```python
"hash": hashlib.sha256(str(details).encode('utf-8')).hexdigest()
```

以及測試：

```python
assert len(log["hash"]) == 64
```

**原因：**

只雜湊 `details`，沒有涵蓋 timestamp 與 event type；攻擊者可把 `DENY_PERMISSION` 改成 `EXECUTE_SUCCESS` 而不改 hash。更重要的是，測試只檢查長度，任意 64 字元字串都能通過。

日誌本身是公開可變 list，呼叫者可執行 `logger.events.clear()` 或直接改 entry。這對教學 mock 可以接受，但不能稱為「確保」完整性。

**最小修法：**

事件雜湊應涵蓋 timestamp、type、details、前一筆 hash，並提供 `verify()` 實際重算。測試至少篡改一筆 `type` 或 `details`，確認驗證失敗。另把安全結論限制為「示範可驗證結構」，不要聲稱記憶體 list 已不可竄改。

---

## 二、狀態、失敗與重試契約缺漏

### 9. 沒有章綱要求的狀態機與重試策略

**原句：**

> 理解如何通过狀態機記錄每一次操作的生命週期，包括請求、驗證、執行（若允許）、結果與審計日誌。

實作只記錄：

> `EXECUTE_START`、`EXECUTE_SUCCESS`、`EXECUTE_ERROR` 及若干 `DENY_*`

**原因：**

沒有 call ID，無法可靠地把 START、SUCCESS、ERROR 關聯到同一次調用；也沒有 `RECEIVED`、`VALIDATED` 等狀態，更沒有合法轉移。章綱特別包含「狀態與失敗重試」，本章卻沒有區分：

- schema/permission 等永久失敗，不應重試；
- 暫時性讀取失敗，可有限重試；
- handler 已產生未知結果時是否安全重試；
- 重試次數、退避與最終狀態。

雖然 mock 只讀查詢通常可重試，但稽核寫入仍會重複，且未受控的 handler 並不保證冪等。

**最小修法：**

加入單調遞增的本機 `call_id`，每筆事件包含它；定義最小狀態轉移：

`RECEIVED -> VALIDATED -> EXECUTING -> SUCCEEDED/FAILED`

拒絕則：

`RECEIVED -> DENIED`

只對明確的 `TransientReadError` 重試最多固定次數；JSON、schema、permission、unknown tool 不重試。每次 attempt 記錄編號。無須真的 sleep，以免拖慢測試。

---

### 10. 例外訊息直接回傳，可能洩露內部資訊

**原句：**

```python
except Exception as e:
    self.logger.log("EXECUTE_ERROR", {"error": str(e)})
    return {"status": "error", "message": str(e)}
```

**原因：**

任意 handler 的例外字串可能含路徑、查詢內容或內部資料。正文自己提醒日誌敏感資訊，主程式卻同時把原始錯誤寫入日誌並回傳給呼叫者。

**最小修法：**

對外只回固定錯誤碼，如 `TOOL_EXECUTION_FAILED`；稽核端也只記錄受控的例外類別名稱與 call ID，不記錄任意訊息。若要保留診斷文字，必須明示這只是無敏感資訊的 mock。

## 三、測試與例題問題

### 11. SQL 注入例題的字元描述不正確

**原句：**

> 字符串包含 `;`、`/`、`-` 等非法字符。

**原因：**

示例字串 `"O2 level; DROP TABLE sensors; --"` 不含 `/`。雖不影響拒絕結論，但逐步手算應精確。

**最小修法：**

刪除 `/`，寫成包含分號與連字號。

---

### 12. 現有安全測試未驗證 handler 沒有被呼叫

**原句：**

> 不執行任何資料庫查詢。

**原因：**

目前只檢查返回狀態，沒有以計數器或 sentinel 驗證被拒絕時 handler 確實未執行。就現有控制流而言預期不會執行，但故障測試應直接核對這個安全性質。

**最小修法：**

增加一個記憶體計數 handler；在 unknown tool、permission deny、schema deny 後斷言計數仍為零。這不需要外部工具。

---

### 13. 缺少若干必要邊界與故障測試

至少缺少：

- top-level JSON 是 list、數字或 `null`；
- `tool` 不是字串；
- `params` 不是 dict；
- 額外 top-level 欄位；
- `limit=True`；
- `limit=0`、負值、超過上限；
- 超長字串；
- handler 拋出暫時與永久錯誤；
- 重試達上限；
- 稽核鏈遭竄改；
- 同名工具重複註冊；
- `current_role` 被任意改寫的信任邊界。

**最小修法：**

不需大量重寫，補一組表驅動測試即可。每個拒絕案例同時核對狀態、錯誤碼、事件類型及 handler 呼叫次數。

---

### 14. `call` 的頂層結構沒有顯式驗證

**原句：**

```python
call = json.loads(json_call) if isinstance(json_call, str) else json_call
tool_name = call.get("tool")
```

**原因：**

若合法 JSON 是 `[]` 或 `null`，會進入廣泛的 `except Exception`，被記為 `EXECUTE_ERROR`，而不是輸入契約拒絕。這混淆了不合法請求與工具執行故障。

**最小修法：**

解析後先檢查 `type(call) is dict`，再要求頂層鍵恰為 `{"tool", "params"}`，並將違反記為 `DENY_CALL_SCHEMA`。

## 四、案例、資料與能力聲稱

### 15. 養殖案例引入未提供的模型能力與真實閾值口吻

**原句：**

> 模型通過學習歷史數據，隱式地學到了這些維度之間的相關性（幾何結構）。

以及：

> 發現 DO-03 的溶解氧值持續下降，低於安全閾值 6.0 mg/L。

**原因：**

本章沒有建立或訓練該模型，也沒有提供 DO-03 資料。全卷約定又明示養殖資料全部合成、無真實操作閾值。因此不能把「已學到」與「安全閾值」寫成事實。這不是要求本章加入完整 Transformer；本章並未宣稱提供完整 Transformer，故不必重複模型或訓練 loop，但案例必須標為假設性。

**最小修法：**

改成「假設上游模型提出下降判讀」及「示例規則門檻 6.0，僅供合成演示，不是真實養殖安全建議」。並說明 Agent 不取代現場專業判斷。

---

### 16. 過度保證「確保」安全

**原句：**

> 這種設計確保了即使模型被攻擊或出現故障，也無法對生產環境造成實體或數據損失。

以及：

> 系統確保了AI Agent僅作為“觀察者”與“分析者”

**原因：**

現有程式接受任意 handler，沒有 OS 沙箱、網路隔離或能力限制；稽核器本身也可變。它只能在明示假設下減少風險，不能確保對生產環境無損失。即使真正唯讀，也可能造成查詢型拒絕服務、敏感資料外洩或錯誤建議。

**最小修法：**

改為條件式表述：「在 handler 封閉受信、程序無網路/設備能力、資料權限正確且資源限制生效的前提下，可防止本例所列的直接寫入與設備控制；仍不排除資訊洩露、資源耗盡與人類誤採建議。」
