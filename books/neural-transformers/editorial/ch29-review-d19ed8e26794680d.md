## 總評

本輪稿件相較更早版本已修正習題 3 的空字串問題；目前：

```python
return isinstance(s, str) and len(s) > 0 and all(c == "a" for c in s)
```

與 `^a+$` 的非空語義一致，所附四個斷言也合理。這一項不再構成疑慮。

重新核對目前章稿後，主架構大致成立：

- 模型輸出只作提議；
- 工具表、角色與 Schema 由程式端控制；
- 未提供 shell、網路或設備 handler；
- `bool` 不會冒充整數；
- 參數及結果須可用受控 JSON 表示；
- 同一次調用使用穩定 `call_id`；
- `max_retries` 明確表示首次嘗試以外的額外次數；
- 命題把受保護業務狀態與稽核狀態分開；

但習題 2 仍有一項確定的虛假能力聲明，例題一仍與程式返回值不一致，重試失敗事件仍未進入稽核，且幾個新防護分支尚未有故障測試。依本卷「自足程式、完整解答、正常／邊界／故障測試」的要求，仍需修訂。

## 一、阻擋項：習題 2 宣稱不存在的名稱拒絕規則

### 逐字原句

> `# set_alert_threshold 不註冊，因為它包含寫入操作，且名稱不以 get/read/query 開頭會被 register_tool 拒絕`

### 實際程式

`register_tool()` 對名稱只做：

```python
if not isinstance(tool_name, str) or not tool_name:
    raise ValueError(...)
if tool_name in self.tools:
    raise ValueError(...)
```

目前沒有任何：

```python
startswith("get_")
startswith("read_")
startswith("query_")
```

檢查。

### 自行重算

下列程式符合目前所有註冊條件，因此會成功：

```python
gateway.register_tool(
    "set_alert_threshold",
    {},
    ["admin"],
    lambda p: {"ok": True}
)
```

所以答案聲稱它「會被 `register_tool` 拒絕」是錯誤的。

### 原因

本章真正的安全邊界應是受信任初始化程式只建立固定 allowlist，而不是名稱。名稱為 `get_data` 的 handler 仍可能寫檔，名稱為 `render_export_preview` 的 handler 也可以完全只在記憶體中運算。

### 最小修法

不要恢復名稱前綴規則。將註解改為：

> `set_alert_threshold` 不在受信任初始化程式建立的固定 allowlist 中，因此所有角色均拒絕；模型與一般使用者不能呼叫 `register_tool()`。名稱本身不證明唯讀性。

題目既稱「權限矩陣」，答案應明列：

| 工具 | monitor | analyst | admin |
|---|---:|---:|---:|
| `get_sensor_data` | Allow | Allow | Allow |
| `get_historical_report` | Deny | Allow | Allow |
| `render_export_preview` | Deny | Deny | Allow |
| `set_alert_threshold` | Deny | Deny | Deny |

## 二、例題一與實作的業務結果結構不一致

### 逐字原句

> 工具內部發現 `PH-02` 不存在，返回 `{"error": "Sensor not found"}`。

### 實際程式

```python
return {"ok": False, "error": "Sensor not found"}
```

### 原因

本章以兩層狀態區分：

1. handler 是否正常完成；
2. 業務查詢是否成功找到資料。

`SUCCEEDED` 表示 handler 正常完成；`ok: False` 才表示查無資料。例題漏掉 `ok`，使這個區分不完整。

### 最小修法

將例題改成：

```json
{"ok": false, "error": "Sensor not found"}
```

並保持 Gateway 記 `SUCCEEDED` 的說明。

## 三、重試功能可用，但稽核沒有記錄每次暫時失敗

### 逐字原句

```python
except TransientReadError as e:
    attempts += 1
    if attempts <= max_retries:
        continue
```

### 事件序列重算

第一次失敗、第二次成功時，現有事件是：

1. `RECEIVED`
2. `VALIDATED`
3. `EXECUTING`, attempt 1
4. `EXECUTING`, attempt 2
5. `SUCCEEDED`

日誌沒有一筆明確表示 attempt 1 發生 `TransientReadError`。稽核者只能從第二次 `EXECUTING` 推測前一次失敗，不能核對：

- 哪個 attempt 失敗；
- 錯誤是否暫時；
- Gateway 是否決定繼續重試；
- 最後一次是否因上限而終止。

### 最小修法

加入狀態：

```python
ATTEMPT_FAILED = "ATTEMPT_FAILED"
```

捕捉後記錄：

```python
attempts += 1
will_retry = attempts <= max_retries
self.logger.log(
    EventStatus.ATTEMPT_FAILED,
    tool_name,
    {
        "attempt": attempts,
        "reason_code": "TRANSIENT_READ_ERROR",
        "will_retry": will_retry
    },
    call_id
)
```

不要記錄原始例外文字。習題 5 的預期事件序列須同步加入 `ATTEMPT_FAILED`。

## 四、`FAILED` 事件沒有共同的機器可讀原因欄位

### 逐字原句

結果不可序列化：

```python
{"error": "result not JSON-serializable"}
```

重試耗盡：

```python
{"error": "Max retries exceeded"}
```

未知 handler 例外：

```python
{"exception_type": type(e).__name__}
```

### 原因

三者都使用 `FAILED`，但 details 結構不同，稽核程式必須解析自由文字或猜測欄位。

### 最小修法

統一加入：

```python
"reason_code"
```

分別使用：

- `INVALID_TOOL_RESULT`
- `RETRY_EXHAUSTED`
- `HANDLER_EXCEPTION`

對外 API 的錯誤碼無須改動。

## 六、Schema 註冊期的型別檢查不完整

### 1. `min`、`max` 可直接引發 TypeError

### 逐字原句

```python
if min_val is not None and max_val is not None and min_val > max_val:
```

例如：

```python
{"x": {"type": "int", "min": "1", "max": 10}}
```

會比較字串與整數，拋出 `TypeError`，而不是清楚的契約 `ValueError`。

### 最小修法

在比較前依欄位型別驗證上下界。int 邊界須排除 bool；float 邊界須有限。

---

### 2. Enum 元素型別未驗證

以下 schema 可被註冊：

```python
{"x": {"type": "int", "enum": [1, True, "2"]}}
```

Python 中 `True == 1`，會造成 enum membership 混淆。

### 最小修法

註冊時逐一核對 enum 元素與欄位型別。

---

### 3. `max_length` 未驗證

`max_length=True` 會被當作 1；負值會拒絕所有非空字串；字串上限可能在執行時造成比較錯誤。

### 最小修法

要求：

```python
type(max_length) is int and max_length >= 0
```

---

### 4. 角色元素未驗證

`allowed_roles` 外層雖是 collection，但元素可能是整數或不可雜湊 list。後者會在 `set(allowed_roles)` 拋 `TypeError`。

### 最小修法

要求每個角色都是非空字串。

## 七、受限域定義與實作不一致

### 逐字原句

> 字串必須匹配正規表達式且長度 $\le L_{max}$。

但習題 2 使用：

```python
{"sensor_id": {"type": "str"}}
```

既沒有 pattern，也沒有 `max_length`。

### 最小修法

二選一：

1. 所有字串欄位強制提供有限 `max_length`；或
2. 將正文的「必須」改成「可由 pattern 與／或最大長度限制」。

本章處理不可信輸入，建議採第一種。

## 八、AuditLogger 的一致性問題

### 1. 事件 JSON 未拒絕 NaN

參數與結果都使用 `allow_nan=False`，事件序列化卻沒有。

### 最小修法

```python
json.dumps(
    event_dict,
    sort_keys=True,
    separators=(",", ":"),
    allow_nan=False
)
```

---

### 2. `event_seq` 在序列化成功前增加

### 逐字原句

```python
self.event_seq += 1
...
payload = self._serialize_event(event_body)
```

若序列化失敗，事件未 append，但序號已被消耗。

### 最小修法

先計算候選序號，成功序列化、計算 hash 及 append 後才更新 `self.event_seq`。

---

### 3. `verify_chain()` 未核對序號連續

應增加：

```python
if entry["event"].get("event_seq") != i + 1:
    return False
```

並核對：

```python
self.event_seq == len(self.events)
```

這不會防止整鏈重寫或尾端截斷；章首已正確承認該限制。

## 九、唯讀命題與測試計數器的狀態邊界

### 逐字原句

> 被註冊的工具實現本身是封閉且可信的，且不具備寫入或網路能力

但 handler 執行：

```python
HANDLER_CALL_COUNT += 1
```

這是記憶體寫入。它不修改 `MOCK_SENSOR_DATA`，可視為測試 instrumentation 而非 $S_{\text{protected}}$，但必須明示。

### 最小修法

補充：

> `HANDLER_CALL_COUNT` 只屬於測試觀測狀態，不屬於受保護業務狀態；正式唯讀 handler 不包含此計數副作用。

命題後可再補一個推論：未通過 allowlist、授權或 Schema 的提議不進入 handler，因此受保護狀態不變，只追加 `DENIED` 事件。

## 十、稽核案例與小結措辭

### 1. 兩個 hash 不應彼此匹配

### 逐字原句

> 驗證 `details` 中的參數哈希與工具返回值哈希是否匹配

參數與結果是不同內容，兩個 hash 通常不相等。

### 最小修法

改成：

> 分別對另行保存的原始參數與結果依相同 canonical JSON 規則重算摘要，核對各自的 `params_hash` 與 `result_hash`。

---

### 2. 小結的 hash-chain 能力寫得過強

### 逐字原句

> 可檢測竄改的稽核日誌

章首已正確限定只能檢測未同步重算的部分修改，不能抵抗整鏈重寫或尾端截斷。

### 最小修法

改成：

> 可檢測未同步重算之部分修改的教學用雜湊鏈日誌。

---

### 3. Gateway 不能獨立「確保」handler 唯讀

### 逐字原句

> 確保操作是唯讀的（Read-Only）。

目前唯讀性來自受信任初始化程式只註冊封閉 mock handler，而不是 Gateway 對 handler 能力的分析。

### 最小修法

改成：

> 只允許受信任初始化程式預先註冊的唯讀 mock handler；Gateway 不從工具名稱推導唯讀性。
