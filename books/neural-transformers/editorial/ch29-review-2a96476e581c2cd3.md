## 一、重試中的失敗仍未被稽核

### 逐字原句

```python
except TransientReadError as e:
    # 暫時性錯誤，重試
    attempts += 1
    if attempts <= max_retries:
        continue
```

### 控制流重算

第一次 handler 拋 `TransientReadError`，第二次成功時，目前事件為：

```text
RECEIVED
VALIDATED
EXECUTING attempt=1
EXECUTING attempt=2
SUCCEEDED
```

事件鏈中沒有表示 attempt 1 失敗的事件，也沒有記錄：

- 失敗類別是暫時性錯誤；
- attempt 編號；
- 是否會重試；
- 此次重試是基於剩餘額度，而非任意再次執行。

雖然從完整程式控制流可以推測第一個 attempt 發生了 `TransientReadError`，但日誌本身並不自足。若稽核資料與執行程式版本分離，僅由兩個 `EXECUTING` 無法確定前一次的終止原因。

### 最小修法

增加事件：

```python
ATTEMPT_FAILED = "ATTEMPT_FAILED"
```

捕捉暫時性錯誤後：

```python
attempts += 1
will_retry = attempts <= max_retries
self.logger.log(
    EventStatus.ATTEMPT_FAILED,
    tool_name,
    {
        "attempt": attempts,
        "reason_code": "TRANSIENT_READ_ERROR",
        "will_retry": will_retry
    },
    call_id
)
```

不要記錄 `str(e)`，以免洩露 handler 內部訊息。

習題 5 應同步核對：

```text
RECEIVED
VALIDATED
EXECUTING(1)
ATTEMPT_FAILED(1, will_retry=True)
EXECUTING(2)
SUCCEEDED
```

連續三次失敗時，則應能看到每一個 attempt 的失敗，而不只是三個 `EXECUTING` 加一個總體 `FAILED`。

## 二、`FAILED` 事件缺少共同原因契約

### 逐字原句

結果不可編碼：

```python
{"error": "result not JSON-serializable"}
```

重試耗盡：

```python
{"error": "Max retries exceeded"}
```

其他 handler 例外：

```python
{"exception_type": type(e).__name__}
```

### 原因

三種事件的 status 都是 `FAILED`，但 details 沒有共同欄位。稽核程式若要統計失敗原因，只能解析英文文字或依欄位存在與否猜測類別。

### 最小修法

加入穩定欄位：

```python
"reason_code"
```

分別使用：

```text
INVALID_TOOL_RESULT
RETRY_EXHAUSTED
HANDLER_EXCEPTION
```

例如：

```python
self.logger.log(
    EventStatus.FAILED,
    tool_name,
    {
        "reason_code": "HANDLER_EXCEPTION",
        "exception_type": type(e).__name__
    },
    call_id
)
```

對外 API 的 `INVALID_TOOL_RESULT`、`RETRY_EXHAUSTED`、`EXECUTION_FAILED` 不必更改。

## 三、Schema 註冊期可造成未受控例外

### 3.1 上下界型別未驗證

### 逐字原句

```python
if min_val is not None and max_val is not None and min_val > max_val:
    raise ValueError(f"field {key}: min > max")
```

### 反例重算

若：

```python
{
    "limit": {
        "type": "int",
        "min": "1",
        "max": 100
    }
}
```

Python 會比較 str 與 int，拋出 `TypeError`，不是作者設計的 `ValueError`。

若只有：

```python
{
    "limit": {
        "type": "int",
        "min": "1"
    }
}
```

註冊會成功；執行 `_validate_schema()` 時：

```python
value < min_val
```

才會拋 `TypeError`。外層 Schema 檢查只捕捉 `ToolContractError`，因此這個例外會逸出 `execute_tool_call()`，不會形成 `SCHEMA_VIOLATION`。

### 最小修法

在註冊時驗證每一個非 `None` 邊界：

- int 欄位：`type(bound) is int`；
- float 欄位：非 bool 的 int／float，且 `math.isfinite(bound)`；
- str 欄位：禁止 `min`、`max`。

型別通過後才比較 `min <= max`。

---

### 3.2 `max_length` 型別與範圍未驗證

### 逐字原句

```python
if max_len is not None and len(value) > max_len:
```

以下值目前都能註冊：

```python
"max_length": "100"
"max_length": True
"max_length": -1
```

第一個在執行時產生 `TypeError`；第二個被 Python 當成 1；第三個讓所有非空字串超過上限。

### 最小修法

要求：

```python
type(max_len) is int and max_len >= 0
```

且只有 str 欄位可使用。

---

### 3.3 Enum 元素型別未驗證

以下 Schema 可註冊：

```python
{"type": "int", "enum": [1, True, "2"]}
```

Python 中 `True == 1`，因此：

```python
value in enum_vals
```

不能表示正文宣稱的精確型別契約。

### 最小修法

註冊時逐一核對 enum 元素：

- str：元素必須是 str；
- int：`type(v) is int`；
- float：非 bool 的有限 int／float。

---

### 3.4 角色元素未驗證

### 逐字原句

```python
if not isinstance(allowed_roles, (list, tuple, set)) or not allowed_roles:
    raise ValueError(...)
...
"allowed_roles": set(allowed_roles)
```

如果：

```python
allowed_roles=[["monitor"]]
```

`set(allowed_roles)` 會拋 `TypeError`。如果包含整數，則雖能建立 set，卻破壞角色字串契約。

### 最小修法

建立 set 前要求每一個 role 都是非空字串。

---

### 3.5 未知欄位設定被靜默忽略

例如：

```python
{"type": "str", "max_lenght": 100}
```

拼錯的 `max_lenght` 不會被拒絕，作者可能誤以為限制已生效。

### 最小修法

為 str／int／float 分別建立允許的 field-definition key 集合，遇到未知設定立即 `ValueError`。

---

## 四、正文與實作對字串限制的定義不一致

### 逐字原句

> 字串必須匹配正規表達式且長度 $\le L_{max}$。

但主工具的 `sensor_id` 有 pattern、沒有 `max_length`；習題 2 的：

```python
{"sensor_id": {"type": "str"}}
```

則兩者都沒有。

### 最小修法

二選一：

1. 強制所有字串欄位有有限 `max_length`，pattern 視需求選用；或
2. 將正文改成「字串可由 pattern 與／或最大長度約束」。

由於後文把限制輸入長度列為 ReDoS 防禦，較一致的選擇是至少強制 `max_length`。

## 五、AuditLogger 的序列化與序號提交仍不完整

### 5.1 事件序列化未設定 `allow_nan=False`

### 逐字原句

```python
return json.dumps(
    event_dict,
    sort_keys=True,
    separators=(",", ":")
).encode("utf-8")
```

參數與結果都拒絕 NaN／Infinity，事件卻沒有。Python 預設可輸出非標準 JSON token `NaN` 或 `Infinity`。

### 最小修法

加入：

```python
allow_nan=False
```

---

### 5.2 `event_seq` 在事件成功前遞增

### 逐字原句

```python
self.event_seq += 1
...
payload = self._serialize_event(event_body)
```

若 details 不可序列化，事件沒有 append，但 `event_seq` 已增加，形成序號空洞。

### 最小修法

先建立候選序號：

```python
next_seq = self.event_seq + 1
```

成功序列化、hash 計算及 append 後，才更新：

```python
self.event_seq = next_seq
self.prev_hash = current_hash
```

---

### 5.3 `verify_chain()` 沒有核對事件序號

目前只核對 `prev_hash` 與內容 hash。還應檢查：

```python
entry["event"].get("event_seq") == i + 1
```

最後檢查：

```python
self.event_seq == len(self.events)
```

這不會使記憶體雜湊鏈抵抗整鏈重寫或尾端截斷；只是檢查當前物件內部一致性。

---

### 5.4 非法 entry 可能使驗證拋例外

若 entry 缺少 `"event"`、`"hash"`、`"prev_hash"`，可能拋 `KeyError`；若被改成不可序列化內容，可能拋 `TypeError` 或 `ValueError`。

### 最小修法

在驗證函數中將上述結構／序列化錯誤轉成 `False`，並增加故障測試。

## 六、稽核案例仍誤述兩種 hash 的關係

### 逐字原句

> 驗證 `details` 中的參數哈希與工具返回值哈希是否匹配（需與另行保存的結果重算比較）。

### 原因

`params_hash` 與 `result_hash` 是不同內容的摘要，不應彼此相等。此外：

- `params_hash` 位於 `RECEIVED` 事件；
- `result_hash` 位於 `SUCCEEDED` 事件。

它們甚至不在同一筆 details 中。

### 最小修法

改成：

> 依同一 `call_id` 找出 `RECEIVED` 與 `SUCCEEDED` 事件；對另行保存的原始參數及結果分別依相同 canonical JSON 規則重算摘要，再分別核對 `params_hash` 與 `result_hash`。

## 七、關鍵錯誤分支仍未有故障測試

目前有 14 個測試，但以下明列安全分支未覆蓋。

### 7.1 `INVALID_PARAMS_ENCODING`

應使用含 set 或其他不可 JSON 編碼值的 params，核對：

- 回 `INVALID_PARAMS_ENCODING`；
- handler 未執行；
- 稽核鏈仍維持一致。

### 7.2 `INVALID_TOOL_RESULT`

註冊一個返回 set 的 mock handler，核對：

- 回 `INVALID_TOOL_RESULT`；
- 有 `FAILED`；
- 沒有 `SUCCEEDED`；
- 不重試。

### 7.3 控制鍵注入

使用：

```python
{
    "tool": "get_ph_level",
    "params": {
        "sensor_id": "PH-01",
        "required": []
    }
}
```

預期 `SCHEMA_VIOLATION`，handler 呼叫次數不變。

### 7.4 同名工具重複註冊

第二次註冊同名工具應受控拋 `ValueError`，原 handler 不被覆寫。

### 7.5 註冊期非法 Schema

至少測試：

- int 的 `min` 是字串；
- `max_length=True`；
- enum 含錯誤型別；
- role 含非字串。

修正後都應得到明確 `ValueError`，而不是偶然 `TypeError`。

## 八、唯讀命題與計數器副作用的邊界仍未說明

### 逐字原句

> 被註冊的工具實現本身是封閉且可信的，且不具備寫入或網路能力

但兩個 handler 均執行：

```python
HANDLER_CALL_COUNT += 1
```

這是記憶體寫入。由於命題只保證 $S_{\text{protected}}$ 不變，不保證整個 Python 程序無任何寫入，所以命題可以保留；但需明確分類。

### 最小修法

補充：

> `HANDLER_CALL_COUNT` 僅為測試 instrumentation，屬於測試觀測狀態，不屬於 $S_{\text{protected}}$；正式唯讀 handler 不包含此計數副作用。

## 九、能力聲明仍需限定

### 9.1 Gateway 不能獨立確保 handler 唯讀

### 逐字原句

> 確保操作是唯讀的（Read-Only）。

目前沒有靜態分析、能力沙箱或系統呼叫攔截；只依賴受信任註冊。

### 最小修法

改為：

> 只允許受信任初始化程式預先註冊的唯讀 mock handler；Gateway 不由工具名稱推導或獨立證明 handler 唯讀。

### 9.2 小結的雜湊鏈能力過強

### 逐字原句

> 可檢測竄改的稽核日誌

章首已正確限定其不能抵抗整鏈重寫或尾端截斷。

### 最小修法

改為：

> 可檢測未同步重算之部分修改的教學用雜湊鏈日誌。

### 9.3 「不具破壞性或控制性能力」應限定到本例

`register_tool()` 可以接受任意 callable，因此 Gateway 類本身並不保證無副作用。

### 最小修法

改為：

> 在本章封閉 mock、固定 allowlist、模型不能註冊工具且程序沒有外部能力的假設下，本例只執行輔助監控查詢。
