## 一、習題 2 的工具註冊說明與程式矛盾

### 逐字原句

> `# set_alert_threshold 不註冊，因為它包含寫入操作，且名稱不以 get/read/query 開頭會被 register_tool 拒絕`

### 原因

目前 `register_tool()` 只檢查工具名是否為非空字串及是否重複：

```python
if not isinstance(tool_name, str) or not tool_name:
    raise ValueError(...)
if tool_name in self.tools:
    raise ValueError(...)
```

沒有任何 `get_`、`read_`、`query_` 前綴規則。因此：

```python
gateway.register_tool(
    "set_alert_threshold",
    {},
    ["admin"],
    lambda p: {"ok": True}
)
```

按目前程式會成功註冊，不會因名稱被拒絕。

### 最小修法

不要恢復名稱判斷，因為工具名稱不能證明 handler 唯讀。將註解改成：

> `set_alert_threshold` 不在受信任初始化程式建立的固定 allowlist 中，因此所有角色皆拒絕；模型與一般使用者無法呼叫 `register_tool()`。

題目要求權限矩陣，答案還應明列：

| 工具 | monitor | analyst | admin |
|---|---:|---:|---:|
| `get_sensor_data` | Allow | Allow | Allow |
| `get_historical_report` | Deny | Allow | Allow |
| `render_export_preview` | Deny | Deny | Allow |
| `set_alert_threshold` | Deny | Deny | Deny |

這是程式與完整解答之間的直接事實錯誤。

## 二、習題 3 的字串驗證錯誤接受空字串

### 逐字原句

```python
def is_safe_a_string(s):
    return all(c == 'a' for c in s)
```

作者把它稱為 `^a+$` 的安全替代。

### 自行重算

Python 對空 iterable 的 `all()` 回傳 True，因此：

```python
is_safe_a_string("")
```

結果是 True。若傳入空 list：

```python
is_safe_a_string([])
```

結果同樣是 True。

但 `^a+$` 中的 `+` 要求至少一個 `a`，且題意要求輸入為字符串，所以兩者不等價。

### 最小修法

```python
def is_safe_a_string(s):
    return (
        isinstance(s, str)
        and len(s) > 0
        and all(c == "a" for c in s)
    )
```

補上預期邊界：

```python
assert is_safe_a_string("aaa") is True
assert is_safe_a_string("") is False
assert is_safe_a_string("aa!") is False
assert is_safe_a_string([]) is False
```

這也是確定的完整解答錯誤。

## 三、例題一的業務結果結構與實作不一致

### 逐字原句

> 工具內部發現 `PH-02` 不存在，返回 `{"error": "Sensor not found"}`。

### 實際實作

```python
return {"ok": False, "error": "Sensor not found"}
```

### 原因

- handler 已正常完成，所以 Gateway 記 `SUCCEEDED`；
- 業務結果是感測器不存在。

例題漏掉 `ok`，使正文對 transport success 與業務錯誤的區分不完整。

### 最小修法

將例題返回值改成：

```json
{"ok": false, "error": "Sensor not found"}
```

## 四、重試功能存在，但稽核生命週期漏掉暫時失敗

### 逐字原句

```python
except TransientReadError as e:
    attempts += 1
    if attempts <= max_retries:
        continue
```

### 逐步推算

第一次失敗、第二次成功時，事件實際是：

1. `RECEIVED`
2. `VALIDATED`
3. `EXECUTING`, attempt 1
4. `EXECUTING`, attempt 2
5. `SUCCEEDED`

沒有事件明確說明第一次 attempt 發生 `TransientReadError`，也沒有 `will_retry` 決策。若只要求功能性重試，程式能運作；但章綱要求「狀態與失敗重試」，正文又主張事件溯源，因此應記錄每次失敗。

### 最小修法

增加：

```python
ATTEMPT_FAILED = "ATTEMPT_FAILED"
```

捕捉後記錄：

```python
attempts += 1
will_retry = attempts <= max_retries
self.logger.log(
    EventStatus.ATTEMPT_FAILED,
    tool_name,
    {
        "attempt": attempts,
        "reason_code": "TRANSIENT_READ_ERROR",
        "will_retry": will_retry
    },
    call_id
)
```

習題 5 的預期序列須同步加入 `ATTEMPT_FAILED`。

## 五、`FAILED` 事件沒有統一契約

### 逐字原句

結果不可序列化：

```python
{"error": "result not JSON-serializable"}
```

重試耗盡：

```python
{"error": "Max retries exceeded"}
```

其他例外：

```python
{"exception_type": type(e).__name__}
```

### 原因

三者都是 `FAILED`，卻沒有共同的機器可讀欄位。稽核程式只能解析自由文字或猜測欄位。

### 最小修法

統一加入：

```python
"reason_code"
```

分別使用：

- `INVALID_TOOL_RESULT`
- `RETRY_EXHAUSTED`
- `HANDLER_EXCEPTION`

不必改外部 API 的錯誤碼。

## 七、Schema 註冊期仍有型別缺口

### 1. 上下界比較可能拋 TypeError

### 逐字原句

```python
if min_val is not None and max_val is not None and min_val > max_val:
```

例如：

```python
{"type": "int", "min": "1", "max": 10}
```

會在字串和整數比較時拋 `TypeError`。

### 最小修法

先依欄位 `type` 驗證 `min`、`max` 的型別，再比較大小。int 邊界須排除 bool；float 邊界須有限。

---

### 2. Enum 元素沒有型別驗證

以下 schema 可註冊：

```python
{"type": "int", "enum": [1, True, "2"]}
```

而 Python 中 `True == 1`，membership 容易混淆。

### 最小修法

註冊時逐一驗證 enum 元素與欄位型別一致。

---

### 3. `max_length` 沒有驗證

`max_length=True` 會被當成 1，負值會拒絕所有非空字串，字串型上限會在執行期比較失敗。

### 最小修法

要求：

```python
type(max_length) is int and max_length >= 0
```

---

### 4. `allowed_roles` 元素未驗證

外層雖要求 list、tuple 或 set，但元素可能是整數或不可雜湊 list。後者會在 `set(allowed_roles)` 拋 `TypeError`。

### 最小修法

要求每個角色都是非空字串。

## 九、AuditLogger 的局部一致性問題

### 1. 事件序列化未設定 `allow_nan=False`

參數和結果都拒絕 NaN，事件卻沒有使用相同規則。

**最小修法：**

```python
json.dumps(..., allow_nan=False)
```

### 2. `event_seq` 在序列化前遞增

### 逐字原句

```python
self.event_seq += 1
...
payload = self._serialize_event(event_body)
```

若序列化失敗，事件沒有 append，但序號已增加。

**最小修法：**

先建立候選序號，成功 append 後才更新 `self.event_seq`。

### 3. `verify_chain()` 不檢查序號連續

應檢查：

```python
entry["event"]["event_seq"] == i + 1
```

以及：

```python
self.event_seq == len(self.events)
```

這仍不能抵抗整鏈重算或尾端截斷；正文已正確承認該限制。

## 十、唯讀命題與測試計數器

### 逐字原句

> 被註冊的工具實現本身是封閉且可信的，且不具備寫入或網路能力

但 handler 執行：

```python
HANDLER_CALL_COUNT += 1
```

### 原因

這是可觀察的記憶體寫入。它沒有修改 `MOCK_SENSOR_DATA`，所以可被定義為測試 instrumentation 而非 $S_{\text{protected}}$，但稿件必須明示。

### 最小修法

補一句：

> `HANDLER_CALL_COUNT` 只屬於測試觀測狀態，不屬於受保護業務狀態；正式唯讀 handler 不包含此計數副作用。

另可補推論：未通過 allowlist、角色或 Schema 的提議不會進入 handler，因此受保護狀態不變，只追加 `DENIED` 日誌。

## 十一、稽核案例與小結措辭

### 1. 兩個 hash 不應彼此匹配

### 逐字原句

> 驗證 `details` 中的參數哈希與工具返回值哈希是否匹配

參數與結果是不同內容，它們的 hash 通常不相等。

### 最小修法

改為：

> 分別對另行保存的原始參數和結果依相同 canonical JSON 規則重算摘要，核對各自的 `params_hash` 與 `result_hash`。

### 2. 小結的「可檢測竄改」過強

章首已限定只能檢測未同步重算的部分修改，小結卻省略限制。

### 最小修法

改成：

> 可檢測未同步重算之部分修改的教學用雜湊鏈日誌。

### 3. Gateway 本身不能證明 handler 唯讀

### 逐字原句

> 確保操作是唯讀的（Read-Only）。

### 最小修法

改成：

> 只允許受信任初始化程式預先註冊的唯讀 mock handler；Gateway 不從工具名稱推導唯讀性。
