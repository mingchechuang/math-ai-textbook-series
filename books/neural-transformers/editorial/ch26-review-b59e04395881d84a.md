## 1. 核心數學與定義核對

### 1.1 量化誤差界 (Proposition 26.1)
*   **定義**：$s = \max|x|/q_{max}$。
*   **誤差界**：$|x - \hat{x}| \le s/2$。
*   **證明檢查**：
    *   $x/s \in [-q_{max}, q_{max}]$。
    *   $\text{round}(x/s)$ 產生整數 $m_i$。
    *   若 $x_i/s$ 在 $[-q_{max}, q_{max}]$ 內，$\text{round}$ 後的值不會超出此範圍（因為端點是整數，round會保持在端點或內部）。
    *   Clip 是恆等映射。
    *   $|x_i - s \cdot m_i| = s |x_i/s - m_i| \le s \cdot 0.5$。
    *   **結論**：證明邏輯正確。
*   **零張量處理**：$s=0$ 時約定 $s=1, \hat{x}=0$。避免除零。正確。

### 1.2 蒸餾梯度 (Proposition 26.2)
*   **損失**：$\mathcal{L} = \text{KL}(p || q) = \sum p \log p - \sum p \log q$。
*   **梯度**：$\frac{\partial \mathcal{L}}{\partial z_{s,j}} = \frac{q_j - p_j}{T}$。
*   **證明檢查**：
    *   $\frac{\partial}{\partial z_j} \sum_k p_k \log q_k = \sum_k p_k \frac{1}{q_k} \frac{\partial q_k}{\partial z_j}$。
    *   $\frac{\partial q_k}{\partial z_j} = \frac{1}{T} q_k (\delta_{kj} - q_j)$。
    *   $\sum_k p_k \frac{1}{q_k} \frac{1}{T} q_k (\delta_{kj} - q_j) = \frac{1}{T} \sum_k p_k (\delta_{kj} - q_j) = \frac{1}{T} (p_j - q_j \sum p_k) = \frac{1}{T} (p_j - q_j)$。
    *   因為 KL 是 $-\sum p \log q$ 加上常數，梯度取負號：$-\frac{1}{T}(p_j - q_j) = \frac{1}{T}(q_j - p_j)$。
    *   **結論**：公式正確。
*   **Batch Average**：程式碼中 `grad = (q - p) / (T * N)`。正確。

## 2. 程式碼與實作核對

### 2.1 `softmax_temp` 與數值穩定性
*   使用了 `logsumexp` 減去最大值 $m$。
*   $z/T$ 可能溢位？
    *   若 $z$ 是有限值，$T$ 是有限正數，$z/T$ 可能變大。
    *   `logsumexp` 內部 `z - m` 保證最大為 0，其他為負。
    *   `np.exp(negative)` 不會溢位，可能下溢為 0。
    *   這是標準的穩定實現。
    *   **注意**：程式碼中檢查了 `s = z / T` 是否有限。若 $z$ 極大且 $T$ 極小，$z/T$ 可能變為 `inf`。
    *   檢查：`if not np.all(np.isfinite(s)): raise ValueError`。這會拒絕過大的 logits 除以過小的 T。這是很嚴格的防禦，符合「不讓 NaN 靜默流入」的精神。

### 2.2 `distill_kl_and_grad` 的 NaN 處理
*   問題點：`p_k = 0` 時，`log(p_k)` 是 `-inf`。`p_k * log(p_k)` 是 `0 * -inf = NaN`。
*   程式碼使用 `np.where(p > 0, p * (logp - logq), 0.0)`。
*   **關鍵分析**：`np.where` 是**急切求值** (Eager Evaluation) 嗎？
    *   在 NumPy 中，`np.where(cond, x, y)` 會先計算 `x` 和 `y` 的所有元素，然後根據 `cond` 選擇。
    *   因此，`p * (logp - logq)` 在 `p=0` 的位置仍然會被計算，產生 `NaN`。
    *   但是，`np.where` 的結果在該位置會取 `0.0`。
    *   **結果**：輸出是正確的（0），但中間過程產生了 NaN。
    *   **風險**：如果後續操作對 NaN 敏感（例如某些優化器或特定的數值分析），這可能不是問題，因為結果是 0。但如果希望完全避免中間 NaN，應該使用掩碼索引。
    *   **文檔說明**：文中明確指出「`np.where` ... 會先完整計算兩個分支 ... 該位置的 NaN 會被選為 0.0 而不出現在結果中」。這是對 NumPy 行為的正確描述。
    *   **結論**：實作可行，且文檔誠實描述了底層機制。

### 2.3 逐通道量化
*   `quantize_per_column` 對 `W (Din, Dout)` 沿 `axis=0` 取 max。
*   這意味著對每一**列** (Output Channel) 計算一個 scale。
*   Shape: `max_abs` 是 `(1, Dout)`。
*   `scale` 是 `(1, Dout)`。
*   `W / scale` 廣播正確。
*   **術語核對**：在深度學習中，通常 "Per-Channel" 指輸出通道。這裡的實作符合標準定義。

## 3. 手算與測試案例核對

### 3.1 手算 26.2 (蒸餾)
*   $z_t = [2, 1, 0], z_s = [0, 1, 2], T=2$。
*   $p \approx [0.506, 0.307, 0.186]$。
*   $q \approx [0.186, 0.307, 0.506]$。
*   梯度 $(q-p)/T \approx [-0.16, 0, 0.16]$。
*   **直觀檢查**：
    *   $j=0$: $q_0 < p_0$。學生低估。梯度負。下降方向（負梯度）$z \leftarrow z - \eta(\text{negative}) = z + \dots$。$z$ 變大。$q$ 變大。正確。
    *   $j=2$: $q_2 > p_2$。學生高估。梯度正。下降方向 $z \leftarrow z - \eta(\text{positive})$。$z$ 變小。$q$ 變小。正確。
*   **結論**：手算與直觀解釋完全正確。

### 3.2 邊界測試 B3 (Logits 500, -500)
*   $z_t = [500, -500]$。
*   $m = 500$。
*   $z - m = [0, -1000]$。
*   $\exp([0, -1000]) = [1, 0]$ (下溢)。
*   $p = [1, 0]$。
*   $\log p = [0, -\infty]$?
    *   `logsumexp` 回傳 $\log(\sum \exp) = \log(1) = 0$? 不，`logsumexp` 回傳 $m + \log(\sum \exp(z-m)) = 500 + \log(1) = 500$。
    *   $\log p = (z/T) - \text{LSE} = [500, -500] - 500 = [0, -1000]$。
    *   所以 $\log p$ 是有限值！
*   **關鍵發現**：在穩定 Softmax 實現中，$\log p_k$ 通常**不是** $-\infty$，而是 $z_k - \text{LSE}$。只要 $z_k$ 和 $\text{LSE}$ 都是有限值，$\log p_k$ 就是有限值。
*   **何時會出現 $-\infty$？**
    *   只有在先計算 $p = \exp(\dots)$ 導致下溢為 0，然後再對 $p$ 取 log 時。
    *   但程式碼是直接計算 `logp = st - logsumexp(st)`。
    *   `st` 是有限值，`logsumexp` 是有限值。
    *   所以 `logp` 是有限值。
    *   **問題**：文中說「$p_k \log p_k$ 的極限值是 0... 但 `0.0 * -inf` ... 是 NaN」。
    *   如果 `logp` 是有限值（例如 -1000），而 `p` 是 0.0。
    *   `0.0 * (-1000.0)` 結果是 `0.0`，**不是** `NaN`。
    *   **只有當 `logp` 是 `-inf` 時**，`0.0 * -inf` 才是 `NaN`。
    *   **結論**：在標準的 Log-Softmax 實現中，$p_k$ 下溢為 0 並不會導致 $\log p_k$ 變為 $-\infty$。因此，`p * log p` 不會產生 `NaN`。
    *   **修正**：文中的解釋「避免 p_k=0 搭配 log p_k=-inf 產生 NaN」基於一個**錯誤的前提**，即在該實現中 `logp` 會變成 `-inf`。實際上，由於使用 Log-Softmax 公式，`logp` 保持有限。
    *   **影響**：雖然 `np.where` 是無害的防禦（Defensive Programming），但文檔中對其必要性的解釋（基於 `0 * -inf`）在該特定實現下是不成立的。這屬於**解釋性錯誤**，雖然不影響程式正確性（因為結果都是 0），但影響了讀者對數值穩定性的理解。
    *   **最小修法**：修正對 `np.where` 必要性的解釋。指出在該 Log-Softmax 實現中 `logp` 保持有限，故 `0 * finite` 為 0，`np.where` 主要用於確保數學定義的嚴謹性（定義 $0 \log 0 = 0$）以及防禦可能因不同實現或邊界情況導致 `logp` 非有限的場景，而非單純因為此處會產生 NaN。或者，如果作者堅持 $p$ 下溢後直接取 log 的路徑（雖然程式碼不是這樣寫的），則需澄清程式碼實際路徑與假設路徑的差異。
    *   **深入檢查**：有沒有可能 `logsumexp` 本身溢出？
        *   `logsumexp` 內部減去 max，所以不會溢出。
        *   回傳值可能很大（例如 500），但有限。
        *   `st` 也是有限的（假設輸入有限且 T 足夠大使得 st 有限，程式碼檢查了 st 有限）。
        *   所以 `logp` 確實有限。
    *   **判定**：這是一個技術細節上的解釋錯誤。需要修正文檔說明，以免誤導讀者以為 Log-Softmax 會產生 $-\infty$。

## 5. 總結與建議

章節整體質量很高，數學推導嚴謹，程式碼自足且包含充分的邊界檢查。主要問題在於對 `np.where` 處理 `0 * -inf` 的解釋與實際 Log-Softmax 實現的特性不符。雖然程式碼是安全的，但解釋應更精確。

**最小修法建議：**
在「實作與程式」章節中，修改對 `np.where` 的說明。
原句：「須注意 NumPy 的 `np.where` 不是「先判斷再乘」... 因此 `p=0` 位置的乘積仍會被求值，但該位置的 NaN 會被選為 `0.0`...」
建議修改為：「在本實現中，`logp` 透過 `z/T - logsumexp(z/T)` 計算，即使 `p` 下溢為 0，`logp` 仍為有限值，故 `p * logp` 不會產生 NaN。使用 `np.where` 是為了嚴格遵循 $0 \log 0 = 0$ 的數學定義，並防禦未來可能更改為先計算 `log(p)` 的實現，或是當 `z` 極端導致 `logsumexp` 溢出（雖然已檢查）時的安全網。」
