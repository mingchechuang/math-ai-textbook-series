## 1. 現行架構與觀察範圍

- 五模型，各8個角色，共40個持久化會話角色；作者與逐章審稿者採不同模型。
- Volume II有30章，輪派給20作者及20審稿者。40角色不代表40個同時執行的研究單位，也不是OS層級沙箱。
- 最多4個章節工作；DeepSeek與Qwen各最多1個請求，OpenAI供應者最多2個。
- 逐章流程含初稿、審稿、有限修訂；之後有第三模型主編精準patch與跨章檢查。
- 已有輸入／輸出、session、錯誤、歷史稿、內容雜湊快取及有限呼叫預算；應保留這些能力，不必為改版全部推倒。

## 2. 六個明確改進方向

### 2.1 格式驗證與內容驗證分離（優先處理）

**實際觀察**

- 「第十三章」被只接受阿拉伯數字的章標題檢查拒絕。
- Markdown清單內Python圍欄的共同縮排，被正規表示式原樣取出送入AST，導致`unexpected indent`。
- 檢查到的多個縮排失敗片段，在去除共同縮排後可通過AST；這只證明原先的語法拒絕可能來自提取方式，不表示程式語義已正確。
- 輸出驗證失敗後雖保留拒絕稿，但重試只改attempt，未完整帶入具體診斷，容易再犯相同錯誤或重寫整章。

**證據位置**（專案根目錄相對路徑）

- `books/modern-graphics/editorial/rejected-000020.txt`、`rejected-000023.txt`：第8章清單內程式縮排。
- `rejected-000033.txt`、`rejected-000048.txt`：第9章中文章號／小節格式及縮排。
- `rejected-000037.txt`、`rejected-000038.txt`：第13章中文章號。
- `rejected-000042.txt`、`rejected-000064.txt`：第14章標題及缩排。
- 對應`error-ch*-*.json`及`book2_editor.py`的`validate()`、`Editor.invoke()`。

**建議**

1. 章號、標題等可確定的結構由程式統一組裝；模型負責正文。
2. 使用CommonMark／Markdown解析器提取程式區塊，尊重清單容器縮排，而不是對整份Markdown做簡單regex提取。
3. 僅正規化可證明等價的格式，保留原稿及差異。不能任意刪縮排掩蓋真正Python錯誤。
4. 格式錯誤先本機修復；內容錯誤才交模型。
5. 重試提供錯誤位置、原輸出及修訂範圍，避免同提示盲目再生成。

### 2.2 審稿意見也需要獨立驗證

**實際觀察**

第11章一份審稿指出法線朝向問題，但其建議修法的叉積符號仍錯誤：

```text
(1, 0, 0) × (1, -0.1, 0.1)
```

審稿寫成`(0, 0.1, 0.1)`；主編以獨立標準庫算式核對，結果為：

```text
(0, -0.1, -0.1)
```

證據：`books/modern-graphics/editorial/ch11-review-47abd88d085b6942.json`。此例顯示審稿提出的修改不能直接當作已證明正確，也不能據此推定整章所有內容都有問題。

**建議**

- 加入獨立數值驗證角色／工作，而不只增加另一份自然語言審稿。
- 對座標往返、法線正交與繞序、梯度有限差分、射線交點、蒙皮bind pose等建立不變量與反例測試。
- 測試期望值應由契約、獨立計算或可信基準推導，不能直接複製作者的錯誤輸出形成自我驗證。
- 對爭議先提供可重現證據，再由主編裁決；多模型投票不等於数学證明。
- 生成程式先經檢視，才在禁止網路及敏感檔案存取、限制CPU／記憶體／時間的環境執行。不得直接自動執行所有模型程式。

### 2.3 問題清單取代單純「審稿長文→整章重寫」

**實際觀察**

目前主要以長文傳递審稿及修訂要求。第一卷曾出現一輪修完後又冒出其他問題，或文字規範被當成新阻擋條件；修改正確段落也可能引入新錯誤。

**建議的問題紀錄**

```json
{
  "id": "G11-001",
  "chapter": 11,
  "source_revision": "內容雜湊",
  "category": "math_or_code",
  "severity": "blocking",
  "location": "sweep_circle的三角形索引",
  "claim": "法線朝內",
  "evidence": "指定三個頂點與叉積計算",
  "acceptance": "法線與指定外向方向內積大於0",
  "owner": "指定作者或主編",
  "status": "open"
}
```

- 分開管理必須修正、可選建議、審稿誤判及尚未確認的問題。
- 每項問題固定ID，記錄提出、修訂、驗證與結案的版本。
- 新出現的重大問題仍可阻擋，但須另立問題並附證據，不能隱藏在文風要求中。
- patch只修改定位到的必要內容；驗證通過後鎖定已解決問題，除非有新證據。

### 2.4 跨章契約應提前驗證

**實際觀察**

Volume I曾在逐章通過後，才由跨章審查發現梯度方向、權重形狀與術語不一致。Volume II的座標、深度、UV、色彩與骨架接口會使這種問題更昂貴。

**建議**

- 全書契約不只是一段prompt，還應有版本化的機器可讀schema與參考程式。
- 建立相依章節圖，先核定被後續章節依賴的介面及慣例。
- 對左右手系、相機朝向、NDC深度、UV方向、四元數分量順序、色彩空間與蒙皮矩陣顺序，建立明確測試。
- 每完成一組相依章節就做接口檢查，最後才做完整閱讀與統稿。
- 契約改版時，只使真正受影響的章節、測試與審稿快取失效；不能無條件沿用舊批准。

### 2.5 角色身份與任務會話分離

**觀察與風險**

目前角色有持久化session，且會重複負責不同章節。這有利於維持上下文，但也存在過時契約、前章內容與歷史錯誤滲入新任務的風險。此處是架構風險，不是已量化證明的主要失敗原因。

**建議**

- 保留穩定角色身份、模型配置、專長與稽核關係。
- 每個「章節×階段×版本」使用任務級上下文或獨立session。
- 明確提供當前契約、相關原稿、未結案問題、必要前置章節摘要，而非整段長聊天歷史。
- 定期檢查跨模型審查能帶來哪些獨有錯誤發現；不同模型並不構成統計上的完全獨立。
- 40角色數量暫時保留，不先用增加角色數來解決流程問題。

### 2.6 階段佇列與可觀測性

**實際觀察**

章節工作執行緒會等待另一供應者的審稿資源；初稿可能已存於editorial，但章節頁仍未呈現初稿完成。僅顯示「通過章數」不容易辨別正在工作、等待資源、格式失敗或真正內容退修。

**建議**

分離階段佇列：

```text
章級契約
  → 初稿
  → 格式正規化／靜態檢查
  → 經檢視後的受控数值測試
  → 獨立內容審稿
  → 問題清單／精準修補
  → 受影響測試與複審
  → 相依章節檢查
  → 統稿與出版
```

- 各模型供應者獨立佇列，任務等待時不長時間占用章節工作執行緒。
- 角色session如仍保留，必須防止並行寫入同一session。
- 網頁顯示：初稿完成、等待模型、驗證失敗、待修訂、複審中、通過、預算／服務阻塞。
- 加入心跳、完成／失敗通知與主編待辦清單，避免無聲停止後由使用者追問。
- 保留有限預算與重試邊界，但把「需要主編處理」和「需要使用者改變範圍／預算」分開。

## 3. 建議的新分工（設計方向，未實作）

| 工作 | 責任 | 不應混淆 |
|---|---|---|
| 主編／契約管理 | 章級規格、接口、問題裁決與版本 | 不直接把多數票當真理 |
| 作者 | 推導、例題、實作及必要修訂 | 不自證程式已跑過 |
| 格式／靜態檢查器 | Markdown、章節結構、Python語法、引用格式 | 不判斷數學真偽 |
| 數值驗證工作 | 不變量、反例、獨立基準與受控測試 | 不自動執行未審查程式 |
| 獨立審稿者 | 教學與實質錯誤審查、檢視驗證證據 | 審稿建議本身也可被證據推翻 |
| 整合編輯 | 跨章接口、難度遞進、重複與矛盾 | 不等到整卷最後才介入 |
| 排程／監控 | 依賴、資源、成本、心跳、狀態及通知 | 角色數不等於實際並行度 |

以上是功能責任，不必各新增一個LLM角色；能由程式確定處理的工作，不應交由模型反覆生成。

## 5. 改版驗收與比較方法

以凍結的小批章稿／故障案例先做離線回放，不直接在正在執行的Volume II上切換框架。保留舊結果與新結果，逐項比较：

- 格式誤拒率、相同原因重試次數、整章重生成比例。
- 章節首次通過率與各輪次分布（明確定義分母）。
- 每個真正解決問題的呼叫量、token、估價成本與等待時間。
- 審稿誤判率、修訂引入的新錯誤、結案問題重新打開的原因。
- 數值測試覆蓋的核心不變量與反例，而非只計測試數量。
- 快取是否精確失效、恢復後是否重複呼叫、預算到達時是否正確留下待辦。
- 未審查程式不執行、敏感資料不暴露、失敗不被標成完成。

新流程不能只追求更高批准率；必須同時確認它不是藉由放鬆實質檢查取得數字改善。
